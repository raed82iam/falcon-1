# GOV-SEC-001 — Falcon Security Authority Charter

**Identifier:** GOV-SEC-001  
**Version:** 1.0  
**Status:** Approved  
**Effective Date:** 2026-07-25  
**Approval Record:** GOV-013  
**Owner:** Falcon Constitutional Authority  
**Governing Authority:** Falcon Vision; Falcon Constitution; GOV-000; GOV-AUT-001; AUT-001 v1.1; SEC-001; SEC-002; ADR-I005  
**Affected Domains:** All  
**Implementation Authority:** Not Granted

## 1. Purpose

GOV-SEC-001 establishes the charter, jurisdiction, appointment model, powers, limits, accountability, emergency authority, review duties, and succession rules of the Falcon Security Authority.

Its purpose is to ensure that security governance is competent and decisive without becoming an unrestricted source of operational, financial, constitutional, or self-expanding authority.

> **Security Authority protects Falcon's trust conditions. It does not own Falcon's purpose or create permission to use capital.**

## 2. Charter Effect

Approval of this Charter establishes the Security Authority's governance model.

Approval alone does not:

- appoint a permanent Security Authority holder;
- delegate an operational permission;
- activate cryptographic material;
- approve a Crypto Profile;
- authorize implementation;
- authorize production deployment;
- create financial authority; or
- transfer the Project Owner's constitutional powers.

Appointment and delegation require separate Authority Instruments recorded under GOV-000 and GOV-AUT-001.

## 3. Jurisdiction

The Falcon Security Authority has jurisdiction over the governance of Falcon's security and trust-protection conditions, including:

- security policy;
- identity assurance requirements;
- authentication protection;
- cryptographic profiles;
- cryptographic domains and purposes;
- key and secret governance;
- information classification protection requirements;
- trust boundaries;
- security control requirements;
- vulnerability treatment;
- security exceptions;
- compromise declarations;
- security-related suspension recommendations and delegated emergency suspensions;
- trust-restoration security criteria;
- dependency and supply-chain security requirements;
- security evidence requirements; and
- security review of self-maintenance and evolution.

This jurisdiction governs security conditions. It does not grant general authority over every activity affected by security.

## 4. Excluded Jurisdiction

The Falcon Security Authority does not possess jurisdiction to:

- amend or reinterpret the Vision;
- amend the Constitution;
- create financial objectives;
- authorize trading, investing, brokerage, market access, or live-capital exposure;
- accept financial risk merely because security controls are adequate;
- operate Guardian outside Guardian's constitutional mandate;
- grant operational permission belonging to another authority;
- approve architecture or implementation outside security conformance;
- govern product priority or commercial strategy;
- waive higher-authority obligations;
- erase, conceal, or rewrite evidence;
- appoint itself;
- expand its own jurisdiction;
- approve its own material exception;
- conclusively resolve a material challenge to its own decision; or
- restore its own unrestricted authority after material compromise.

## 5. Governing Position

The Falcon Security Authority is subordinate to:

1. the Falcon Vision;
2. the Falcon Constitution;
3. the competent Constitutional and Project Owner authority;
4. approved governance instruments defining its jurisdiction; and
5. all higher applicable obligations.

It operates alongside, not above:

- Guardian;
- Authority Engine;
- Recovery Authority;
- Persistence and Evidence Authorities;
- Verification Authorities;
- Promotion Authority; and
- domain-specific authorities.

No peer relationship permits one authority to consume another's jurisdiction.

## 6. Security Authority Functions

The Falcon Security Authority may, within valid assignment and delegation:

- propose security policy;
- define security requirements;
- maintain governed security catalogs;
- classify security risk;
- review security designs and exceptions;
- approve security-specific artifacts where explicitly authorized;
- approve or change Crypto Profile lifecycle state where explicitly delegated;
- declare security controls inadequate;
- require remediation;
- issue security restrictions within delegated scope;
- initiate protective escalation;
- recommend Guardian restriction;
- suspend unsafe cryptographic or security use under valid emergency authority;
- define security evidence required for restoration;
- participate in independent restoration review;
- challenge unsafe decisions;
- require preservation of security evidence; and
- report unresolved security risk to the competent higher authority.

Each function remains bounded by its Authority Instrument.

## 7. Internal Roles

The Charter recognizes the following separable security roles:

### 7.1 Security Policy Authority

Governs security policy and mandatory protection requirements within delegated jurisdiction.

### 7.2 Cryptographic Profile Authority

Governs Crypto Profile proposals, lifecycle decisions, migration requirements, and prohibited use within delegated jurisdiction.

### 7.3 Cryptographic Domain Catalog Authority

Governs Domain IDs, Purpose IDs, protection-profile references, lifecycle status, and catalog integrity.

### 7.4 Security Exception Authority

Evaluates bounded exceptions to subordinate security policy where higher authority permits exception.

### 7.5 Security Incident Authority

Coordinates security classification, containment requirements, security evidence, and escalation during suspected or confirmed compromise.

### 7.6 Security Restoration Reviewer

Assesses whether the security conditions required for restoration have been satisfied.

### 7.7 Security Assurance Authority

Determines whether security verification obligations and evidence satisfy the declared security scope.

These roles MAY be held by one person during the Foundation stage only where independence is not constitutionally or normatively required. Role concentration SHALL be explicit and SHALL NOT eliminate independent technical controls or independent approval requirements.

## 8. Appointment

A Security Authority holder SHALL be appointed only through a valid Authority Instrument issued by the competent appointing authority.

The appointment SHALL identify:

- holder identity;
- assigned security role or roles;
- jurisdiction;
- powers;
- excluded powers;
- consequence ceiling;
- permitted environments;
- effective date;
- term;
- review date;
- delegation rights;
- emergency powers;
- conflict-of-interest obligations;
- evidence duties;
- suspension and removal authority;
- succession arrangement; and
- acceptance by the holder.

Appointment SHALL be recorded in GOV-000 or its governed successor.

No job title, technical ownership, access to secrets, system role, expertise, or prior practice constitutes appointment.

## 9. Transitional Custody

Until a permanent Security Authority holder is separately appointed:

- the Project Owner acting as current Constitutional Authority retains approval responsibility for Crypto Profiles and permanent lifecycle decisions;
- technical security actors may inspect, recommend, test, and escalate only within their separately granted authority;
- no component may infer Security Authority from implementation ownership;
- emergency protective mechanisms retain only the authority already granted by higher documents; and
- this Charter does not silently transfer custody.

Transitional custody SHALL be reviewed before production or live-capital authority is considered.

## 10. Delegation

Security Authority may be delegated only under GOV-AUT-001.

Every delegation SHALL declare:

- jurisdiction;
- exact security role;
- permitted decisions;
- prohibited decisions;
- consequence ceiling;
- environment;
- term;
- redelegation rule;
- emergency authority;
- independence requirements;
- evidence obligations; and
- revocation conditions.

Delegation SHALL NOT:

- create security jurisdiction;
- transfer non-delegable constitutional authority;
- grant financial or operational authority;
- permit self-appointment;
- permit self-expansion;
- bypass Guardian;
- permit the delegate to approve its own material exception;
- permit silent redelegation; or
- survive expiry, suspension, or revocation of its source.

## 11. Cryptographic Profile Governance

Each Crypto Profile SHALL use the lifecycle:

- `DRAFT`;
- `APPROVED`;
- `ACTIVE`;
- `DEPRECATED`;
- `RETIRED`; and
- `FORBIDDEN`.

Lifecycle authority SHALL be explicit:

- `DRAFT` may be created by authorized security design or research authority.
- `APPROVED` requires the competent Cryptographic Profile Authority.
- `ACTIVE` requires the competent Cryptographic Profile Authority and all required evidence and operational approvals.
- `DEPRECATED` requires an attributable lifecycle decision and migration plan.
- `RETIRED` requires confirmation that new protection is prohibited and historical use is bounded.
- `FORBIDDEN` requires competent permanent authority, except that valid emergency authority may impose immediate temporary prohibition pending review.

Only an `ACTIVE` profile may create new Approved protection.

No lifecycle decision grants operational authority to perform a protected business action.

## 12. Algorithm and Profile Decisions

Every material algorithm or Crypto Profile decision SHALL identify:

- decision identity;
- jurisdiction;
- deciding authority;
- profile identity and version;
- proposed lifecycle transition;
- security basis;
- standards and evidence;
- affected domains and purposes;
- affected keys and roots;
- affected artifacts and retained data;
- compatibility;
- downgrade risk;
- migration;
- rollback;
- effective time;
- review date;
- uncertainty;
- dissent;
- challenge path; and
- required downstream action.

A profile SHALL NOT become `ACTIVE` solely because:

- an algorithm is widely used;
- a provider supports it;
- tests pass;
- it was previously accepted elsewhere;
- it is the newest option;
- it is the easiest option; or
- no known attack is currently public.

## 13. Domain Catalog Governance

The Cryptographic Domain Catalog Authority SHALL govern:

- Domain IDs;
- Purpose IDs;
- environment scope;
- identity scope;
- protection profile;
- permitted operations;
- independent-root requirements;
- lifecycle state;
- ownership;
- effective version;
- deprecation;
- migration; and
- historical interpretation.

Domain IDs and Purpose IDs are immutable.

They SHALL NOT be:

- reassigned;
- repurposed;
- reinterpreted;
- created as free text by components;
- silently aliased;
- deleted from historical interpretation; or
- reused after retirement.

Changed meaning requires a new governed identifier.

## 14. Canonical Encoding Boundary

The Security Authority may define security meaning and required protected fields.

It SHALL NOT create independent canonical encoding rules where FCE-001 governs representation.

FCE-001 remains the sole authority for canonical encoding. CRY-001 and security catalogs define governed values and semantics without redefining serialization.

## 15. Key and Secret Governance

The Security Authority governs policy for:

- key purpose;
- domain separation;
- independent root boundaries;
- generation;
- custody;
- activation;
- access;
- distribution;
- rotation;
- overlap;
- revocation;
- compromise;
- recovery;
- retirement;
- destruction; and
- evidence.

It SHALL NOT:

- possess raw key material merely because it governs policy;
- treat key custody as authority to use protected capabilities;
- approve unrecorded key use;
- permit cross-purpose key use;
- weaken independent-root requirements for convenience; or
- expose secrets in governance evidence.

Policy authority, custody, use authority, and verification SHOULD remain separated according to consequence.

## 16. Security Exceptions

A security exception is valid only when higher governing policy permits exceptions.

Every exception SHALL be:

- explicit;
- attributable;
- justified;
- risk-assessed;
- scoped;
- time-bounded;
- consequence-bounded;
- assigned to an accountable owner;
- protected by compensating controls;
- independently reviewable;
- evidenced;
- monitored;
- revocable; and
- subject to expiry without silent renewal.

The Security Authority SHALL NOT approve:

- an exception to the Vision or Constitution;
- plaintext fallback where higher policy prohibits it;
- hidden acceptance of material vulnerability;
- an exception that creates financial authority;
- its own material conflict without independent approval;
- removal of Guardian protection;
- evidence concealment; or
- permanent authority through repeated temporary exceptions.

Repeated exceptions SHALL trigger policy or design review.

## 17. Emergency Security Authority

Emergency Security Authority exists only when separately delegated to contain an imminent or credible material security threat.

It MAY:

- suspend a Crypto Profile;
- temporarily treat a profile as prohibited;
- suspend affected keys, identities, trust paths, dependencies, or communication boundaries;
- require isolation;
- require preservation of evidence;
- request or trigger previously authorized Guardian restriction;
- prohibit new protected creation under an affected profile;
- require Safe Mode where already authorized; and
- escalate to the competent higher authority.

It SHALL:

- use the minimum necessary restriction;
- state the triggering evidence;
- define affected scope;
- record uncertainty;
- be immediately attributable;
- be time-bounded;
- preserve recovery capability where safe;
- prohibit silent downgrade;
- notify required authorities;
- enter independent review; and
- expire unless lawfully renewed or converted by competent permanent authority.

Emergency Security Authority SHALL NOT:

- activate a new Crypto Profile;
- grant operational permission;
- authorize financial action;
- create enduring authority;
- amend higher policy;
- destroy evidence;
- restore unrestricted authority; or
- convert its temporary prohibition into a permanent `FORBIDDEN` decision without competent review.

## 18. Declaring `FORBIDDEN`

A permanent `FORBIDDEN` lifecycle decision requires:

- competent Cryptographic Profile Authority;
- valid jurisdiction;
- evidence of unacceptable risk;
- affected-use inventory;
- immediate restriction plan;
- retained-data and recovery treatment;
- migration plan;
- exception policy limited to isolated recovery when lawful;
- Guardian and operational impact assessment;
- effective time;
- notification;
- independent review appropriate to consequence; and
- immutable decision evidence.

Where delay could create unacceptable harm, delegated Emergency Security Authority may impose temporary prohibition before permanent review.

No component may independently classify a profile as permanently `FORBIDDEN`.

## 19. Relationship to Authority Engine

The Security Authority defines or approves security policies and Security Authority Instruments within its jurisdiction.

Authority Engine:

- verifies jurisdiction and Authority Chain;
- evaluates applicable security constraints;
- enforces valid suspension, revocation, expiry, and prohibition;
- denies unverified or insufficient authority;
- records authorization evidence; and
- does not create security policy.

The Security Authority SHALL NOT:

- bypass Authority Engine where operational authorization is required;
- directly convert policy approval into action permission;
- instruct Authority Engine to ignore higher restrictions;
- issue an Authority Instrument outside its jurisdiction; or
- treat an Authority Engine permit as proof that the underlying security judgment is correct.

## 20. Relationship to Guardian

Security Authority and Guardian have distinct responsibilities:

- Security Authority governs security conditions, profiles, policy, and security assessments.
- Guardian protects capital and system survival through lawful protective restriction.

Security Authority may notify, recommend, challenge, and—where an Approved Contract permits—request a Guardian restriction.

Security Authority SHALL NOT:

- override Guardian;
- suppress a lawful Guardian restriction;
- order Guardian to increase authority;
- restore authority that Guardian lawfully restricts;
- reinterpret Guardian as a security-policy executor; or
- use security approval to compel unsafe operation.

Guardian MAY impose a stricter restriction than Security Authority recommends when required by its governing mandate.

Removal of a security cause does not automatically remove a Guardian restriction.

## 21. Relationship to Recovery

Security Authority defines the security conditions required for recovery from compromise.

Recovery Authority leads authorized recovery action.

Security Authority SHALL NOT be the sole authority that:

- executes recovery;
- declares its own controls restored;
- validates evidence it exclusively produced;
- restores unrestricted authority; or
- closes a material incident involving its own failure.

Return to unrestricted authority requires the independent confirmation prescribed by governing policy.

## 22. Relationship to Evidence and Persistence

Security decisions, assessments, exceptions, suspensions, profile transitions, challenges, and restorations SHALL produce Trust Objects governed by SEC-002.

Security Authority may define confidentiality, integrity, retention, and access requirements.

It SHALL NOT:

- rewrite historical evidence;
- declare missing evidence present;
- treat encryption as proof of truth;
- treat persistence success as proof of correctness;
- conceal unfavorable evidence;
- destroy evidence under review; or
- become the sole completeness authority for evidence it materially produced or transformed.

## 23. Relationship to Verification and Promotion

Security Authority defines applicable security obligations and may evaluate security outcomes within delegated scope.

It does not automatically possess:

- Evidence Completeness Authority;
- Release Promotion Authority;
- constitutional approval;
- deployment authority; or
- acceptance authority for non-security risk.

No component that produces, transforms, aggregates, evaluates, or signs security evidence may be the sole authority declaring the complete release case promotion-ready.

## 24. Relationship to Self-Maintenance and Evolution

Security Authority SHALL review security impact where self-maintenance or evolution affects:

- identity;
- authority;
- trust boundaries;
- cryptographic profiles;
- keys or secrets;
- security controls;
- evidence;
- recovery;
- Guardian;
- dependencies; or
- protected data.

Security Authority SHALL NOT:

- allow self-maintenance to bypass change governance;
- let Falcon approve its own material security change;
- grant self-evolution constitutional authority;
- permit a changed security control to validate itself exclusively;
- allow generated security policy to become active by production alone; or
- treat repeated success as permanent security authority.

## 25. Security Decision Classes

Security decisions SHALL be classified at least as:

- advisory finding;
- mandatory remediation;
- bounded exception;
- profile proposal;
- profile approval;
- profile activation;
- profile deprecation;
- profile retirement;
- temporary emergency prohibition;
- permanent `FORBIDDEN` decision;
- key or identity suspension;
- compromise declaration;
- restoration assessment;
- security acceptance;
- risk escalation; and
- challenge resolution.

Each class SHALL have:

- jurisdiction;
- eligible authority;
- consequence ceiling;
- required evidence;
- independence rule;
- effective-time rule;
- expiry or review rule;
- appeal path; and
- downstream enforcement rule.

## 26. Security Decision Evidence

Every material Security Authority decision SHALL preserve:

- Decision ID;
- decision class;
- subject;
- scope;
- jurisdiction;
- Authority ID and complete Authority Chain;
- decision maker;
- policy baseline;
- evidence;
- assumptions;
- uncertainty;
- affected systems and Trust Objects;
- consequence;
- decision;
- conditions;
- effective time;
- expiry or review;
- dissent;
- conflict-of-interest disclosure;
- challenge path;
- notification;
- supersession; and
- integrity identity.

Missing evidence SHALL reduce the authority or permitted consequence of the decision.

## 27. Independence and Conflict of Interest

A Security Authority holder SHALL disclose material conflicts before exercising affected authority.

The holder SHALL recuse when governing policy requires.

The Security Authority SHALL NOT be the sole authority that:

- approves its own material exception;
- validates its own recovery from compromise;
- resolves a material challenge to its own decision;
- accepts evidence it alone produced as complete;
- promotes its own security change;
- investigates an allegation of its own misconduct conclusively; or
- renews its own appointment.

Low-impact self-correction may occur only under explicit policy and preserved independent audit.

## 28. Challenge and Appeal

Every material Security Authority decision SHALL be challengeable.

A Challenge SHALL identify:

- challenged decision;
- grounds;
- affected jurisdiction;
- security and operational consequence;
- challenger;
- supporting evidence;
- requested interim protection;
- reviewing authority;
- independence requirement;
- decision deadline where urgent; and
- resolution.

A Challenge does not automatically suspend a decision unless governing policy, Guardian, or competent authority requires suspension.

A challenged Security Authority SHALL NOT conclusively validate itself in a material dispute.

## 29. Review Obligations

The Falcon Security Authority SHALL conduct or commission periodic review of:

- its active jurisdiction and delegations;
- role concentration;
- conflicts of interest;
- active Crypto Profiles;
- deprecated, retired, and forbidden profiles;
- domain and purpose catalogs;
- independent-root assumptions;
- key and secret lifecycle policy;
- active exceptions;
- emergency actions;
- security incidents;
- restoration decisions;
- unresolved challenges;
- dependency risk;
- security evidence quality;
- authority use;
- drift; and
- succession readiness.

Review frequency SHALL be proportionate to consequence and change rate.

## 30. Suspension and Removal

A Security Authority holder may be restricted, suspended, or removed by the competent appointing or higher authority when:

- jurisdiction is exceeded;
- evidence is concealed or altered;
- material conflict is unmanaged;
- authority is self-expanded;
- higher obligations are violated;
- competence is materially insufficient;
- required review is persistently avoided;
- trust is compromised;
- the appointment expires;
- the role is no longer necessary; or
- succession is activated.

Suspension or removal SHALL propagate to delegated authority according to GOV-AUT-001 and AUT-001 v1.1.

Historical decisions remain preserved and SHALL be reviewed according to consequence.

## 31. Succession

Every permanent Security Authority appointment SHALL define succession.

Succession SHALL preserve:

- jurisdiction continuity;
- active restrictions;
- Crypto Profile lifecycle state;
- Domain Catalog interpretation;
- key and secret governance;
- incidents;
- exceptions;
- open challenges;
- evidence custody;
- decision history;
- unresolved risk; and
- accountability.

Succession SHALL require:

- competent appointment;
- verified successor identity;
- explicit acceptance;
- conflict disclosure;
- bounded transition period;
- evidence transfer;
- revocation of predecessor access and delegated authority where required; and
- update of GOV-000.

Possession of prior credentials SHALL NOT constitute succession.

## 32. Failure and Uncertainty

When Security Authority identity, jurisdiction, Authority Chain, decision evidence, conflict state, or trust cannot be established:

- new permissive security decisions SHALL be denied;
- unsafe or uncertain security use SHALL be restricted;
- existing protective restrictions SHALL remain in force;
- Guardian SHALL be notified where material harm is possible;
- the competent higher authority SHALL be notified;
- evidence SHALL be preserved;
- uncertainty SHALL be explicit; and
- restoration SHALL require independent review.

Absence or failure of Security Authority SHALL NOT cause plaintext fallback, security downgrade, evidence destruction, or automatic restoration of authority.

## 33. Governance Requirements

- **GOV-SEC-001-REQ-001:** Security Authority SHALL operate only within explicitly assigned security jurisdiction.
- **GOV-SEC-001-REQ-002:** Approval of this Charter SHALL NOT by itself appoint a Security Authority holder.
- **GOV-SEC-001-REQ-003:** Appointment and delegation SHALL use valid Authority Instruments under GOV-AUT-001.
- **GOV-SEC-001-REQ-004:** Security Authority SHALL NOT create financial, operational, constitutional, or general Guardian authority.
- **GOV-SEC-001-REQ-005:** Security Authority SHALL NOT expand its own jurisdiction, powers, term, or delegation rights.
- **GOV-SEC-001-REQ-006:** Crypto Profile lifecycle decisions SHALL be attributable, evidence-based, scoped, effective-dated, and issued by competent authority.
- **GOV-SEC-001-REQ-007:** Only an `ACTIVE` Crypto Profile may create new Approved protection.
- **GOV-SEC-001-REQ-008:** Permanent `FORBIDDEN` status SHALL require competent permanent authority and independent review proportionate to consequence.
- **GOV-SEC-001-REQ-009:** Delegated emergency authority MAY impose immediate temporary prohibition but SHALL NOT create permanent status by itself.
- **GOV-SEC-001-REQ-010:** Domain IDs and Purpose IDs SHALL be immutable and SHALL NOT be reassigned or repurposed.
- **GOV-SEC-001-REQ-011:** Security Authority SHALL NOT redefine canonical encoding governed by FCE-001.
- **GOV-SEC-001-REQ-012:** Security policy authority SHALL NOT imply possession or use authority over keys and secrets.
- **GOV-SEC-001-REQ-013:** Security exceptions SHALL be explicit, bounded, evidenced, independently reviewable, and incapable of waiving higher obligations.
- **GOV-SEC-001-REQ-014:** Emergency Security Authority SHALL be minimal, temporary, attributable, reviewable, and non-renewing by default.
- **GOV-SEC-001-REQ-015:** Security Authority SHALL NOT override or silently remove a lawful Guardian restriction.
- **GOV-SEC-001-REQ-016:** Security Authority SHALL NOT bypass Authority Engine where operational authorization is required.
- **GOV-SEC-001-REQ-017:** Security Authority SHALL NOT be the sole authority restoring its own unrestricted authority after material compromise.
- **GOV-SEC-001-REQ-018:** Material security decisions and evidence SHALL conform to SEC-002.
- **GOV-SEC-001-REQ-019:** Security Authority SHALL NOT be the sole authority declaring a release case complete or promotion-ready when it materially produced or evaluated the evidence.
- **GOV-SEC-001-REQ-020:** Every material security decision SHALL remain attributable, scoped, verifiable, reviewable, and independently challengeable.
- **GOV-SEC-001-REQ-021:** A challenged Security Authority SHALL NOT conclusively validate itself in a material dispute.
- **GOV-SEC-001-REQ-022:** Suspension, removal, expiry, or revocation SHALL constrain dependent delegated authority.
- **GOV-SEC-001-REQ-023:** Succession SHALL require competent appointment and SHALL NOT arise from credential possession.
- **GOV-SEC-001-REQ-024:** Failure or absence of Security Authority SHALL fail safely and SHALL NOT cause security downgrade.
- **GOV-SEC-001-REQ-025:** Transitional custody SHALL remain with the Project Owner acting as current Constitutional Authority until a separate appointment is recorded.

## 34. Conformance Evidence

Conformance requires evidence that:

- Charter approval does not appoint a holder;
- no technical role can infer Security Authority;
- appointment requires a valid Authority Instrument;
- authority outside security jurisdiction is denied;
- Crypto Profile lifecycle transitions require competent authority;
- emergency suspension is temporary and independently reviewed;
- permanent `FORBIDDEN` status cannot be self-declared by a component;
- Domain IDs cannot be repurposed;
- key custody does not create key-use authority;
- Security Authority cannot bypass Authority Engine;
- Security Authority cannot override Guardian;
- removal of a security cause does not automatically restore Guardian-restricted authority;
- security exceptions cannot waive higher obligations;
- self-maintenance cannot self-approve material security change;
- security evidence remains immutable and challengeable;
- Security Authority cannot approve its own material exception or recovery alone;
- suspension propagates to dependent delegations;
- succession revokes predecessor authority as required; and
- absence or failure causes restriction rather than downgrade.

Operational exercise of independently delegated Security Authority requires:

- a separate appointment and Authority Instrument;
- GOV-000 update;
- CRY-001 Cryptographic Domain and Profile Catalog;
- FCE-001 Falcon Canonical Encoding Specification;
- DESIGN-SEC-001 Foundation Cryptographic Provider and Secret Custody Design;
- security decision-class and consequence-class definitions;
- Crypto Profile lifecycle procedure;
- security exception procedure;
- incident and compromise procedure;
- security restoration and independent-review procedure;
- succession record;
- applicable Contracts;
- TRC-001 traceability; and
- PIPE-001 verification gates.

## 36. Foundational Rules

> **Security governance is not operational permission.**

> **Key custody is not key-use authority.**

> **Profile approval is not profile activation. Profile activation is not permission to act.**

> **Emergency suspension protects; it does not govern permanently.**

> **Security Authority may restrict unsafe trust. It may not expand its own power.**

> **No security decision outranks the purpose and authority from which it derives.**
