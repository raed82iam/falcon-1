## 3. Scope of renewed implementation authority

WP-05 may implement only Foundation-owned technical:

- resource pressure truth;
- preemption/reclamation eligibility truth without execution;
- observed enforcement-state truth without mutation;
- deterministic transition stability;
- freshness/expiry/supersession and evidence identity;
- exact global/Application scope separation;
- constituent Application identity preservation for later aggregate-coordinator consumption;
- fail-closed behavior required by the accepted v0.4 plan;
- dedicated WP-05 verification and predecessor regression required to prove the implementation.

## 4. Explicit non-authorities

This authorization DOES NOT authorize:

- WP-06 request/decision implementation;
- WP-07 reclamation/redistribution/rebalance/restoration execution;
- FSARM internal redistribution engine or coordination-envelope execution;
- WP-08 load-shedding/projection implementation;
- Guardian/Safe-State authority;
- Application business logic or Application branch changes;
- runtime activation, production activation or financial authority.

The accepted FSARM coordination-envelope semantic is preserved for later separately gated work and SHALL NOT be prematurely implemented inside WP-05.

## 5. Existing unvalidated implementation

Implementation work previously produced through `a8e1dc1befa85b451f9a2a6cfa75e26d544860a8` is not accepted automatically.

Before reuse, each relevant file SHALL be reconciled against WP-05 v0.4. TARC-hard-bound assumptions or behavior outside the accepted v0.4 scope SHALL be removed or corrected before validation.

## 6. Verification and closure boundary

Implementation success does not close WP-05.

After implementation:

1. dedicated WP-05 executable verification;
2. WP-01 through WP-04 predecessor regression;
3. architecture/security/full relevant regression;
4. fresh post-implementation Red-Team;
5. FCR handoff for Application compatibility verification where required;
6. separate Owner closure decision.

are still required.
