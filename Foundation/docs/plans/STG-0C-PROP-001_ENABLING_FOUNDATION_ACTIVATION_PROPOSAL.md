## 1. Purpose

This proposal defines the next eligible Falcon phase:

```text
Stage 0C — Enabling Foundation Activation
```

Stage 0C exists to evaluate exact Stage 0B candidates and, only through separate competent decisions, activate the minimum enabling Foundation subjects required to establish an independently governed implementation boundary for a later Stage 1 proposal.

This document is a proposal only.

It does not authorize Activation, candidate reconstruction, build, execution, verification, key or secret creation, environment use, Stage 1, production, cloud deployment, financial connectivity, or financial activity.

## 2. Relationship to Prior State

Stage 0B is complete and closed under GOV-053.

The eleven Stage 0B subjects are accepted only as conforming, non-operational candidates within their preserved local Windows verification scope.

Stage 0B completion establishes eligibility to propose Stage 0C. It does not:

- activate a candidate;
- admit a Provider Profile;
- establish operational identity or time;
- establish operational cryptographic custody;
- activate an environment;
- activate a Build Baseline, Pipeline, Gate, or trace expansion;
- authorize Stage 1;
- or make Falcon operational.

## 3. Stage Identity

Stage 0C is a bounded Activation-evaluation phase.

It is not:

- general Falcon implementation;
- Core behavior implementation;
- Self-Awareness implementation;
- Guardian implementation;
- financial-domain implementation;
- an operational Falcon release;
- production;
- cloud deployment;
- or authority to begin Stage 1.

Activation in Stage 0C means reliance on one exact subject for one exact Foundation enabling scope under explicit limits.

It does not mean unrestricted trust, runtime operation, production use, or financial authority.

## 4. Prime Objective Alignment

Stage 0C serves:

```text
Protect Capital
→ Manage Capital
→ Grow Capital
```

Its contribution is protective:

- prevent candidate material from entering trust without independent evaluation;
- prevent test material from becoming operational material;
- prevent circular self-Activation;
- establish restriction and revocation before reliance;
- preserve exact evidence and non-authorities;
- and prevent Stage 1 from beginning on an ambiguous Foundation.

If Activation and protection conflict, protection prevails.

## 5. Eligible Activation Subjects

Only the following subjects may be considered:

1. Canonical Encoding realization for the declared Foundation scope.
2. Trust Object primitives for Foundation evidence.
3. Randomness Provider Profile.
4. Time Provider Profile.
5. Identifier Provider Profile.
6. Cryptographic Provider Adapter Profile.
7. Secret Provider Profile.
8. Certificate and Identity Provider Profile.
9. Exact local Windows Foundation Build Verification Environment Profile.
10. Exact Build Baseline.
11. Exact machine-readable trace expansion.
12. Exact Pipeline Definition.
13. Exact Gate Profile and Evidence Requirement Set generation rules.

The Stage 0B isolated verification Fixture is never an Activation subject.

Each eligible subject requires its own:

- immutable identity;
- Candidate Manifest;
- accepted Root Verification Evidence Set;
- Validity Assessment;
- Evidence Completeness Decision;
- independent review;
- Activation Authority Instrument;
- Activation Decision;
- Activation Manifest;
- restriction and revocation path;
- and explicit non-authorities.

No group Activation by implication is permitted.

## 6. Candidate Is Not Active

A candidate remains non-active until every required Activation decision is valid and applicable to the exact subject.

The following shall not establish Activation:

- successful construction;
- successful build;
- a passing verification result;
- a valid Manifest;
- a valid signature;
- evidence completeness;
- Project Owner acceptance of Stage 0B;
- repository publication;
- source-code presence;
- dependency availability;
- or another subject’s Activation.

Validity, completeness, acceptance, Activation, and reliance remain separate decisions.

## 7. No Promotion of Test Material

Stage 0B material shall remain permanently non-operational.

The following shall never be promoted into active Foundation custody:

- synthetic keys;
- synthetic secrets;
- test roots;
- test certificates;
- test identities;
- deterministic entropy;
- test nonces;
- test Runtime Epochs;
- bootstrap identity or time;
- candidate environment state;
- and verification-only trust anchors.

Any active security or identity profile shall require separately governed clean material created within its approved active custody boundary.

This proposal does not authorize creation of that material.

## 8. Activation Dependency Sequence

Stage 0C shall avoid circular Activation through an explicit sequence.

### 8.1 Step A — Evidence Reconstruction

Before considering any Activation:

- reconstruct Stage 0A and Stage 0B authority;
- reconstruct the .NET boundary event and remediation;
- verify candidate source and evidence identities;
- verify explicit non-authorities;
- confirm cleanup;
- and establish the frozen Stage 0C Evidence Requirement Set.

### 8.2 Step B — Non-Provider Foundations

Evaluate separately:

- Canonical Encoding realization;
- Trust Object primitives;
- and machine-readable trace source expansion.

These are enabling realizations, not operational authority.

### 8.3 Step C — Source Providers

Evaluate separately:

1. Randomness Provider Profile.
2. Time Provider Profile.

Neither may certify its own source quality or Activation.

### 8.4 Step D — Dependent Providers

After applicable source profiles are active:

1. Identifier Provider Profile using active Time and Randomness dependencies.
2. Cryptographic Provider Adapter Profile using active Randomness and approved custody.
3. Secret Provider Profile using active cryptographic custody.
4. Certificate and Identity Provider Profile using active Crypto, Secret, Time, trust-anchor, and revocation policy.

Dependency Activation does not grant consumer Activation automatically.

### 8.5 Step E — Environment

Evaluate and, if independently approved, activate one exact Windows Foundation Build Verification environment.

Environment Activation shall not imply:

- Falcon runtime Activation;
- Foundation implementation;
- production;
- cloud;
- or financial authority.

### 8.6 Step F — Build, Trace, Pipeline, and Gate

After applicable Provider and environment prerequisites:

- activate one exact Build Baseline;
- activate one exact machine-readable trace expansion;
- activate one exact Pipeline Definition;
- and activate one exact Gate Profile.

Each requires a separate decision.

### 8.7 Step G — Readiness Case

Construct the Foundation Implementation Readiness case only after all applicable Stage 0C decisions are complete.

The readiness case may recommend whether Stage 1 should be proposed.

It shall not authorize Stage 1.

## 9. Environment Boundary

The first eligible environment is local Windows.

It shall:

- remain a Foundation build-and-verification environment only;
- remain separate from production;
- remain separate from operational Falcon;
- deny financial connectivity;
- deny Oracle Cloud use;
- use exact admitted tools and dependencies;
- preserve external bootstrap origin where applicable;
- use active Provider Profiles only within their declared Foundation scope;
- enforce cleanup, restriction, suspension, revocation, and expiry;
- and remain portable through Falcon Contracts and Adapters.

Windows remains the first platform, not Falcon’s identity.

Linux and Oracle Cloud remain future directions.

## 10. Provider Activation Boundary

Every Provider Activation shall identify:

- exact Provider implementation digest;
- Provider Profile ID and version;
- supported capabilities;
- environment and Deployment Profile;
- dependencies and their active states;
- configuration identity;
- custody and security profile;
- health and trust conditions;
- restrictions;
- expiry and review conditions;
- evidence identity;
- Activation Decision;
- and exact non-authorities.

A Provider may be active only for its declared scope.

Provider Activation shall not grant:

- business authority;
- financial authority;
- operational Falcon authority;
- production trust;
- or authority to activate a dependent subject.

## 11. Security and Custody Boundary

Stage 0C security evaluation shall require:

- approved Crypto Domains and Purpose IDs;
- canonical Domain Context;
- independent roots where independent compromise boundaries are required;
- key-use enforcement;
- test/active material separation;
- no raw-key export;
- no secret leakage;
- revocation and rotation;
- no platform-default trust;
- no weak or plaintext fallback;
- current Guardian restrictions;
- and non-secret reconstructable evidence.

No active secret or key may enter source, configuration, environment variables, logs, commands, evidence, or ordinary component memory.

Unknown custody state is restrictive.

## 12. Identity and Time Boundary

Activation shall preserve:

- external bootstrap identity as `BOOTSTRAP_EXTERNAL_ID`;
- external bootstrap time as `BOOTSTRAP_EXTERNAL`;
- candidate output as candidate output;
- active Falcon identifiers as newly governed operational identifiers;
- active Time Observations with declared quality and uncertainty;
- Runtime Epoch boundaries;
- and explicit cross-links without reclassification.

An identifier shall not establish identity, authority, time, or trust.

A Time Observation shall not establish business truth, causality, or authority.

## 13. Activation Manifest

Every Activation subject shall use an `ACTIVATION_MANIFEST` conforming to CON-010.

The Manifest shall identify:

- exact subject and candidate lineage;
- authority and jurisdiction;
- exact environment and profile;
- accepted Root Evidence Set;
- Validity Assessment;
- Completeness Decision;
- independent review;
- Activation Decision;
- activated scope;
- effective time;
- expiry or review condition;
- restrictions and revocation;
- residual uncertainty;
- and explicit non-authorities.

The Manifest shall not activate itself.

## 14. Environment Activation Verification

VPL-BST-006 shall evaluate:

- exact environment identity, class, version, and scope;
- capabilities and isolation;
- Provider dependencies;
- authority and jurisdiction;
- evidence completeness;
- independent review;
- wrong-subject and wrong-profile cases;
- restriction, suspension, revocation, and expiry;
- prevention of self-restoration;
- and reconstruction.

Passing VPL-BST-006 does not imply Foundation Implementation Authority.

## 15. Pipeline and Trace Activation Verification

VPL-BST-007 shall evaluate:

- exact atomic-requirement expansion;
- forward and reverse traceability;
- frozen Evidence Requirement Sets;
- evidence origin, integrity, lineage, and context;
- completeness evaluation;
- authority separation;
- negative and mutation cases;
- exactly one Root Evidence Set per promotion decision;
- Gate weakening prevention;
- self-promotion prevention;
- and independent reconstruction.

Passing VPL-BST-007 shall not promote an FRS-001 artifact.

## 16. Evidence Reconstruction Verification

VPL-BST-008 shall require an independent reviewer to reconstruct:

- every authority stage;
- every candidate and environment identity;
- every tool and dependency;
- every evidence origin;
- every obligation and observation;
- every evaluation and context;
- every validity and completeness decision;
- every Activation decision;
- every correction and supersession;
- and every explicit non-authority.

No undocumented assumption may be required for a material conclusion.

## 17. Restriction, Revocation, and Restoration

Every activated subject shall support:

- restriction;
- suspension;
- revocation;
- expiry;
- replacement;
- and controlled restoration.

A subject shall not:

- modify or suppress its restriction;
- release itself;
- restore itself;
- weaken a stronger restriction;
- treat repair as release;
- or resume unrestricted behavior merely because a dependency returned.

Restoration requires current evidence, independent validation, competent approval, controlled transition, and a new authority decision.

## 18. Evidence Model

Stage 0C shall freeze its Evidence Requirement Set before evidence production.

The Root Verification Evidence Set shall preserve:

```text
Authority and Jurisdiction
→ Frozen Obligations
→ Observed Evidence
→ Derived Evaluations
→ Evaluation Context
→ Validity Assessments
→ Completeness Decisions
→ Independent Reviews
→ Activation Decisions
→ Restrictions and Non-Authorities
```

Every Activation decision shall reference exactly one Root Verification Evidence Set.

Individual sessions shall not serve directly as Activation evidence.

## 19. Authority Separation

No candidate producer, environment preparer, evidence producer, transformer, aggregator, signer, evaluator, or completeness authority may be the sole Activation Authority for the same material case.

Authority shall operate only within declared jurisdiction.

Delegation shall not create jurisdiction.

A challenged producer or decision authority shall not conclusively resolve a material challenge against itself.

## 20. Self-Awareness Boundary

Stage 0C does not implement Self-Awareness, Self-Maintenance, or Evolution.

Future Self-Awareness may consume active enabling services only after separate implementation authority.

It may never:

- create its own authority;
- expand jurisdiction;
- activate itself or another subject;
- modify Vision or Constitution;
- bypass Guardian;
- conceal uncertainty;
- suppress evidence;
- weaken restrictions;
- introduce financial authority;
- or approve its own maintenance or evolution.

## 21. Financial Isolation

Stage 0C shall remain financially sterile.

It shall not use or connect to:

- brokers;
- exchanges;
- banks;
- custodians;
- market-data providers;
- financial accounts;
- real market data;
- orders;
- positions;
- portfolios;
- balances;
- customer financial data;
- or capital.

Any financial material or connection shall stop Stage 0C and trigger evidence preservation and Project Owner review.

## 22. Cloud Boundary

Oracle Cloud is not part of Stage 0C.

Stage 0C shall not:

- log in to OCI;
- create a tenancy, compartment, identity, key, network, compute, storage, database, vault, or other cloud resource;
- install an OCI SDK;
- create cloud credentials;
- deploy Falcon;
- or test cloud runtime behavior.

Cloud readiness may be documented only.

## 23. Stop Conditions

Stage 0C shall stop if:

- authority is missing, unclear, expired, revoked, exceeded, or materially challenged;
- exact subject identity is uncertain;
- evidence is incomplete or invalid;
- independent review cannot be maintained;
- candidate and active lifecycle states become ambiguous;
- test material is proposed for active custody;
- a dependency is missing, inactive, stale, or conflicted;
- restriction or revocation cannot be enforced;
- self-Activation, self-restoration, or Gate weakening is attempted;
- an unapproved tool, package, destination, or environment is required;
- secret or protected material escapes custody;
- financial or cloud connectivity appears;
- or Vision, Constitution, Guardian policy, capital protection, or a governing document would be violated.

Failure does not expand authority.

## 24. Exit Criteria

Stage 0C may be assessed complete only when:

- every eligible subject is accounted for;
- every activated subject has an exact Activation Decision and Manifest;
- every non-activated subject has an explicit disposition;
- VPL-BST-006 through VPL-BST-008 pass for the applicable scope;
- every Root Evidence Set is complete and valid;
- authority separation is proven;
- restrictions, revocation, expiry, and restoration controls are proven;
- candidate and active states remain unambiguous;
- no test material entered active custody;
- financial and cloud isolation are confirmed;
- cleanup and preservation are complete;
- unresolved material challenges block closure;
- and the Foundation Implementation Readiness case is produced.

Completion of Stage 0C shall not authorize Stage 1.
