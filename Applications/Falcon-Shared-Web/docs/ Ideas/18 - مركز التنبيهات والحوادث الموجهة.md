# Shared Falcon Web - مركز التنبيهات والحوادث الموجهة

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يكمّل قرارات التنبيهات في الملفات 15 و16 و17، ويستهلك semantics الحالية في FCR-0095 لحالات Guardian/FSATS user-scoped broker/API incidents.

لا يمنح هذا الملف implementation/runtime/trading/authorization authority.

---

## 1. هدف التجربة

المطلوب أن يشعر المستخدم أن Falcon:

- هادئ عندما لا يوجد ما يستحق المقاطعة.
- واضح عندما توجد معلومة مهمة.
- حازم عندما يلزم الانتباه فورًا.
- لا يستخدم نفس مستوى الصراخ لكل شيء.
- لا يجعل المستخدم يتعلم نمط UX جديدًا بلا داعٍ.
- لا يخلط بين ما هو مؤكد وما هو reported أو screenshot-observed أو unknown.

المبدأ:

```text
INTERRUPTION STRENGTH = ACTUAL ATTENTION NEED
```

وShared Web لا يصنع business severity أو authority من نفسه.

---

## 2. الأساس البحثي المستخدم

اختيارات UX هنا تتبع أنماطًا متقاربة في Apple HIG وIBM Carbon وUSWDS:

- notification العادي يكون مختصرًا ويمكن استيعابه بسرعة.
- modal/alert مقاطعة قوية ويستخدم فقط عندما تحتاج الحالة انتباهًا أو قرارًا فعليًا.
- toast مناسب للتغذية الراجعة القصيرة بعد فعل المستخدم.
- inline/banner مناسب لمشكلة مرتبطة بسياق الشاشة.
- unread badge يمثل unread فقط.
- الرسائل القابلة للزوال يجب أن تبقى قابلة للرجوع إليها عندما تكون مهمة.
- الحالة العاجلة تحتاج prominence أكبر، لكن لا يجوز تضخيم urgency غير موثوقة.
- accessibility يجب أن تفرق بين الرسائل العاجلة والرسائل غير العاجلة بدل جعل كل شيء assertive.

هذه مبادئ UX وليست contracts تنفيذية.

## 3. بنية Notification Center لكل Application

كل Application يحتفظ بمركز تنبيهات مستقل كما قرر الـOwner سابقًا.

الواجهة الأساسية تكون بسيطة ومألوفة:

### Header

- عنوان: `التنبيهات`
- unread count صغير عند الحاجة.
- Action بسيط: `تحديد الكل كمقروء` عندما توجد عناصر unread.
- وصول واضح إلى `الأرشيف`.

### Quick filters

الافتراضي:

- `الكل`
- `غير المقروء`

وتظهر category filters فقط عندما يملك الـApplication categories فعلية ومفيدة. Shared Web لا يخترع domain categories.

### Search

بحث بسيط بالعنوان/النص البشري المسموح عرضه.

### Date filter

فلتر تاريخ اختياري عند كثرة العناصر.

### Ordering

```text
ACTIVE NOTIFICATION CENTER = NEWEST FIRST
```

يمكن استخدام فواصل بصرية مثل:

- اليوم
- أمس
- أقدم

بدون كسر الترتيب الزمني.

### Loading

عند العدد الكبير نستخدم lazy loading أو pagination بدل تحميل تاريخ طويل دفعة واحدة.

## 4. شكل عنصر التنبيه

كل عنصر يبقى خفيفًا وقابلًا للمسح البصري السريع:

1. علامة نوع/حالة بسيطة عندما تضيف معنى.
2. عنوان بشري قصير.
3. سطر ملخص واحد، وسطر ثانٍ فقط عند الحاجة.
4. وقت نسبي مثل `قبل 8 دقائق`.
5. unread indicator صغير وغير صاخب.
6. status label فقط عندما يفيد المستخدم، مثل `تم الحل` أو `يتطلب إجراء` إذا كانت authoritative semantics تسمح بذلك.

لا نعرض IDs أو enums أو correlation IDs في القائمة العادية.

التفاصيل التقنية تبقى خلف التفاصيل/السجل عندما تكون مخولة للمستخدم المناسب.

---

## 5. سلوك الفتح

القاعدة المعتمدة تبقى:

```text
OPEN = READ
```

عند فتح عنصر من قائمة الجرس أو Notification Center:

- يفتح Dialog/Popup فوق الصفحة الحالية.
- ينخفض unread count فورًا.
- لا يفقد المستخدم سياق الصفحة.
- `Esc` و`×` يغلقان الـDialog عندما الإغلاق مسموح.
- focus يعود إلى العنصر/المكان المنطقي بعد الإغلاق.

للتنبيه العادي القابل للأرشفة:

```text
× = CLOSE + ARCHIVE
```

للتنبيه الحرج النشط:

```text
× = CLOSE VIEW ONLY
```

ويبقى في Active Center حتى authoritative resolution.

## 6. Empty states

لا نعرض صفحة فارغة باردة.

أمثلة بشرية:

- `ما عندك تنبيهات جديدة.`
- `كل التنبيهات مقروءة.`
- `ما لقينا نتائج تطابق بحثك.`

ولا نضيف رسومات أو رسائل تسويقية داخل empty state لمجرد ملء الفراغ.

---

## 7. Toast / immediate feedback

الـToast يستخدم لرد الفعل القصير على شيء فعله المستخدم للتو.

أمثلة:

- `تم حفظ الإعدادات.`
- `تعذر حفظ التغيير.`

قواعد UX:

- قصير جدًا.
- ثابت في مكان متوقع.
- لا يستخدم لمعلومة يجب على المستخدم الرجوع إليها لاحقًا إلا إذا كان لها سجل آخر.
- لا يحتوي workflow طويلًا.
- إذا فيه Action يحتاج وقتًا، لا يختفي قبل أن يتمكن المستخدم من التعامل معه.

---

## 8. Inline / Banner

المشكلة المحلية تظهر محليًا قدر الإمكان.

```text
LOCAL PROBLEM -> LOCAL MESSAGE
```

مثال:

إذا جزء من بيانات الصفحة غير متاح، يظهر التنبيه قرب ذلك الجزء بدل Modal يقطع كل العمل.

الـBanner يستخدم عندما يؤثر الوضع على نطاق أوسع من جزء صغير، لكن لا يزال لا يحتاج Dialog حتميًا.

## 9. User-targeted urgent/action-required incident من FCR-0095

FCR-0095 عرّف الآن حالة فعلية يجوز فيها للـApplication أن يطلب من Shared Web تنبيهًا عاجلًا وموجهًا لمستخدم محدد مع business/action semantics موثوقة.

عندما تصل semantics موثوقة من الـApplication بأن الطلب:

```text
SPECIFIC PRINCIPAL
+ URGENT / IMMEDIATE ATTENTION
+ ACTION REQUIRED
```

فالـShared Web يعرضه كـ **Immediate Incident Dialog** للمستخدم authenticated المستهدف.

لا يحتاج المستخدم أن يفتح الجرس أولًا.

### شكل الـDialog

الترتيب البصري المقترح:

1. **عنوان واضح جدًا**
   مثال بشري: `تعذر الاتصال بحساب التداول.`
2. **الحقيقة الحالية**
   مثال: `Falcon لا يستطيع حاليًا تأكيد حالة الحساب أو الأوامر عند البروكر.`
3. **آخر وقت مؤكد**
   مثال: `آخر اتصال مؤكد: 10:42 م`
4. **Restriction واضح**
   مثال: `تم إيقاف فتح مخاطر جديدة لهذا الحساب مؤقتًا.`
5. **ما نعرفه / ما لا نعرفه**
6. **الإجراء التالي**
7. زر أساسي مثل `ابدأ التحقق` عندما يكون هذا intent موفرًا ومسموحًا من Application semantics.

لا نستخدم عنوانًا تقنيًا مثل `BROKER_API_FAILURE` في واجهة المستخدم.

---

## 10. Guided incident recovery UX

بعد `ابدأ التحقق` لا نحشر A-to-Z كاملة في شاشة واحدة.

الأسلوب الأفضل للمستخدم هو **step-by-step guided flow**:

- خطوة واحدة أساسية في كل مرة.
- progress واضح مثل `3 من 8` عندما يكون عدد الخطوات معروفًا.
- يمكن للمستخدم الرجوع للخطوة السابقة بدون فقدان ما أدخله.
- Web يعرض بالصيغة البشرية السؤال أو fact/action request الذي يحتاجه Application في اللحظة الحالية.
- Web يرجع للـApplication النتيجة/الدليل المطلوب عبر governed boundary.
- لا نضع checkbox يوحي أن الحقيقة ثبتت لمجرد أن المستخدم ضغط عليه.

```text
APPLICATION REQUESTS BUSINESS FACT/ACTION
-> WEB COMMUNICATES / COLLECTS
-> WEB RETURNS RESULT / EVIDENCE
-> APPLICATION CONTINUES TRADING DECISION
```

```text
USER COMPLETED STEP != BROKER VERIFIED STATE
```

إذا كانت الخطوة مجرد إقرار/تأكيد بشري، تعرض هكذا بصراحة.

---

## 11. Incident truth cards

داخل guided flow نستخدم أربع حالات عرض مفهومة بدل إغراق المستخدم بالمصطلحات الداخلية:

### Confirmed by broker API
واجهة بشرية مثل:
`مؤكد من البروكر`

### Seen in broker screenshot
واجهة بشرية مثل:
`ظاهر في صورة من البروكر`

### Reported by user
واجهة بشرية مثل:
`أبلغتَنا بهذه المعلومة`

### Unknown
واجهة بشرية مثل:
`غير مؤكد حتى الآن`

مع الحفاظ داخليًا على distinctions:

```text
BROKER_API_CONFIRMED
BROKER_UI_SCREENSHOT_OBSERVED
USER_REPORTED
UNKNOWN
```

ولا يتحول screenshot أو user report إلى broker truth بصريًا أو لغويًا.

## 12. Screenshot-assisted recovery UX

عندما يحتاج الـApplication fact/evidence من broker UI، يقرر Shared Web طريقة جمعه وعرضه ضمن UX المملوك للـWeb.

الاختيار الافتراضي:

- يطلب Web صورة محددة واحدة في كل مرة بدل `ارفع صور حسابك` بشكل مبهم.
- مثال: `افتح شاشة Open Positions وارفع صورة واضحة لها.`
- يظهر للمستخدم تنبيه خصوصية قصير قبل الرفع:
  `لا ترفع API key أو كلمة مرور أو رمز تحقق. أخفِ أي معلومات شخصية غير لازمة.`
- بعد الرفع، يظهر status بسيط: `جاري تحليل الصورة` ثم نتيجة ما تمت رؤيته فقط.
- إذا الصورة قديمة/مقصوصة/غير واضحة، يقال ذلك صراحة.
- إذا عاد Application وطلب evidence أحدث بسبب trading/risk semantics، يطلب Web تحديث الدليل بدل الاستمرار على evidence قديم.

طريقة upload، preview، redaction guidance، progress والـacknowledgement هي Web-owned.

---

## 13. Human latency UX

لأن المسار اليدوي بطيء مقارنة بالـAPI، لا نعرض للمستخدم illusion أن المعلومات ما زالت لحظية.

يظهر عمر الدليل بوضوح عند الحاجة:

- `الصورة التقطت قبل 2 دقيقة.`
- `آخر تأكيد من البروكر قبل 6 دقائق.`

إذا أخبر Application أن evidence لم يعد مناسبًا لاستمرار trading recovery، Web يبرز طلب refresh بدل متابعة flow مبني على evidence stale.

Shared Web لا يحدد وحده acceptable risk latency أو market-risk threshold.

---

## 14. Owner-facing incident experience

بالتوازي مع incident الخاص بالمستخدم، يملك Shared Web تجربة Owner مستقلة للتواصل والإشراف.

الـApplication يرسل للـWeb فقط business/trading incident semantics والمعلومة/الإجراء الذي يحتاجه. أما customer contact mechanics والـOwner interaction فهي Web-owned.

واجهة Owner تجمع بشكل واضح بين مصدرين بدون خلط الملكية:

### Application-provided incident truth

- affected trading scope/reference المسموح عرضه.
- incident classification/state.
- known / unknown / stale / screenshot-observed / user-reported / broker-confirmed distinctions.
- trading-risk priority عندما يقدمه Application.
- fact/action المطلوب من المستخدم الآن.
- whether new risk remains restricted.

### Web/account/contact context

- المستخدم/العميل المسموح للـOwner رؤيته.
- وسائل التواصل المتاحة والمسموحة في Web/account context.
- هل المستخدم فتح التنبيه أو رد عبر Web.
- current Web recovery interaction step.
- outreach attempts/status التي يديرها Web.

Action UX المسموح للـOwner يكون من نوع:

- `تواصل مع المستخدم`
- `سجل محاولة تواصل`
- `افتح محادثة الحادث`
- `شاهد المعلومات المطلوبة من Application`

وليس:

- `أغلق الصفقة`
- `أرسل أمرًا`

ما لم يوجد يومًا external/legal/broker authority مستقل وصريح، وهو غير مفترض هنا.

```text
OWNER ESCALATION ROLE != CUSTOMER EXECUTION AUTHORITY
```

## 15. Owner outreach workflow هو Web-owned

إذا المستخدم لا يرد، Shared Web ينسق presentation/contact workflow ضمن البيانات والقنوات المسموح بها.

حالات بشرية مقترحة:

- `لم يرد بعد`
- `تمت محاولة التواصل`
- `تم التواصل هاتفيًا`
- `تم إرسال رسالة`
- `تم الوصول للمستخدم`

مع timestamp/channel حيث يكون ذلك مسموحًا.

الـApplication لا يملك phone/email/SMS workflow ولا contact-attempt tracking ولا user profile/contact-information management.

إذا وصل المستخدم عبر قناة خارجية وقدم نتيجة يحتاجها Application، Web يعيد النتيجة/الدليل المطلوب عبر governed response boundary فقط.

```text
OWNER CONTACTED USER != INCIDENT RESOLVED
WEB RESPONSE TRANSPORT != TRADING DECISION AUTHORITY
```

إذا لا يمكن الوصول للمستخدم ولا يوجد execution path مخول، تعرض limitation بصراحة:

`لا يوجد حاليًا مسار مخول للتحكم في الحساب. سيستمر Falcon بالمراقبة ومحاولات التواصل دون تنفيذ أي إجراء غير مصرح به.`

---

## 16. Credential-recovery presentation

إذا طلب Application semanticًا أن broker credentials تحتاج renewal/replacement/revalidation:

- Application يحدد الحاجة التجارية فقط.
- Shared Web يملك طريقة عرض credential-management UX.
- secret entry لا يتم داخل notification body أو ordinary chat message.
- Web يوجه المستخدم إلى governed secure credential path.
- لا تظهر secret bytes في notifications أو reusable Web state أو contact workflow.

```text
APPLICATION CREDENTIAL RECOVERY REQUIREMENT != WEB CREDENTIAL ENTRY UX
```

---

## 17. Visual attention rules

اختيارات Shared Web القابلة للعكس:

- اللون ليس الوسيلة الوحيدة لفهم الحالة.
- icon + text + hierarchy معًا.
- الأحمر محجوز للحالة التي تستحقه، لا لكل unread.
- unread يستخدم dot/bold treatment خفيف.
- critical active state أقوى بصريًا من informational.
- لا blinking مستمر.
- لا animation متكرر يرهق المستخدم.
- الحركة القصيرة تستخدم فقط لتوضيح وصول/انتقال العنصر.

## 18. Accessibility

- keyboard navigation كاملة.
- focus trap صحيح داخل Dialog الحقيقي فقط.
- عند فتح incident Dialog ينتقل focus إلى عنوان/بداية dialog بطريقة مفهومة.
- عند الإغلاق يعود focus إلى مكان منطقي.
- الرسائل العادية تستخدم announcement غير مقاطع قدر الإمكان.
- الرسائل العاجلة التي تستحق فورًا يمكن أن تستخدم assertive behavior بما يتوافق مع semantics الفعلية.
- icons ليست المصدر الوحيد للمعنى.
- الأزرار labels بشرية وتصف النتيجة.
- hit targets مناسبة.

---

## 19. ما تم اختياره تلقائيًا كـ UX ergonomics

بناءً على Owner rule الذي يسمح للـShared Web بحسم الأمور البديهية القابلة للعكس، تم اختيار التالي بدون طلب قرار Owner منفصل:

- `All / Unread` quick filters.
- Search.
- date filter عند الحاجة.
- newest-first في active center.
- today/yesterday/older visual grouping.
- mark-all-read action.
- lazy loading/pagination عند كثرة السجل.
- empty states البشرية.
- keyboard/focus behavior القياسي.
- عدم استخدام modal للمعلومات العادية.
- immediate dialog للـApplication-requested user-targeted urgent/action-required incident.
- step-by-step incident flow بدل صفحة ضخمة.
- status labels البشرية للحقيقة: broker-confirmed / screenshot-observed / user-reported / unknown.
- focused screenshot requests بدل طلب screenshots عشوائية.
- Web-owned Owner outreach/contact workflow منفصل عن Application business semantics.

كل هذه قرارات presentation/interaction ergonomics ولا تغيّر business authority أو trading truth.

---

## 20. حدود لا يقررها Shared Web

Shared Web لا يقرر:

- من هو target user عندما تكون الهوية جزءًا من Application business incident scope.
- هل trading incident urgent/action-required.
- ما هي trading allowed action intents.
- ما هو broker truth.
- هل screenshot أو user report كافٍ لاتخاذ trading/risk decision.
- متى يصبح evidence stale من منظور trading/risk.
- متى يُرفع no-new-risk restriction.
- متى يعتبر trading incident resolved.
- من يملك portfolio execution authority.

وفي المقابل، Shared Web يملك:

- notification/popup/chat/form/upload mechanics.
- presentation/copy/layout/accessibility.
- Owner/user Web interaction.
- Web-owned customer contact workflow.
- contact-attempt presentation/tracking ضمن Web scope.
- credential-entry presentation subject to security/governed secret boundaries.
