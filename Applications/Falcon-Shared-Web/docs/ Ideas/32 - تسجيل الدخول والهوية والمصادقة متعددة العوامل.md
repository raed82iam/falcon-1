# Shared Falcon Web - تسجيل الدخول والهوية والمصادقة متعددة العوامل

**Status:** `OWNER-DIRECTED SECURITY UX / ACTIVE IMPLEMENTATION INPUT`
**Date:** 2026-08-15
**Branch:** `web-development`
**Scope:** `applications/shared/web/**`

يسجل هذا الملف قرار الـProject Owner بإضافة تسجيل دخول خارجي بحسابات Google وMicrosoft، وتفعيل مصادقة إضافية للعملاء والـProject Owner باستخدام تطبيقات Authenticator مثل Google Authenticator وMicrosoft Authenticator، مع الحفاظ على أن Shared Web لا يصبح مصدر الهوية أو الصلاحيات authoritative من نفسه.

---

## 1. فصل نوعي المصادقة

يوجد مساران مختلفان ويجب عدم خلطهما:

1. **Federated Sign-In / Social-Enterprise Sign-In**
   - `Continue with Google`
   - `Continue with Microsoft`
   - باستخدام OpenID Connect/OAuth 2.0 عبر مزود هوية authoritative.

2. **Multi-Factor Authentication (MFA)**
   - تطبيق Authenticator يولد TOTP أو يستخدم عاملًا أقوى عندما تدعمه الجهة authoritative.
   - Google Authenticator وMicrosoft Authenticator أمثلة عملاء، ولا يجب ربط Falcon بتطبيق واحد بعينه.

```text
GOOGLE_ACCOUNT_SIGN_IN != GOOGLE_AUTHENTICATOR_MFA
MICROSOFT_ACCOUNT_SIGN_IN != MICROSOFT_AUTHENTICATOR_MFA
FEDERATED_IDENTITY != MFA_FACTOR
```

---

## 2. UX المعتمد لواجهة تسجيل الدخول

واجهة FSATS Sign In تعرض:

- البريد/اسم المستخدم + كلمة المرور عندما يكون هذا المسار متاحًا authoritative.
- `Continue with Google`.
- `Continue with Microsoft`.
- إنشاء حساب.
- استعادة الحساب/كلمة المرور حسب العقد authoritative.

بعد نجاح العامل الأول، إذا كانت السياسة تتطلب MFA، ينتقل المستخدم إلى Challenge منفصل وواضح.

```text
PRIMARY_AUTH_SUCCESS != FULL_AUTHENTICATION_WHEN_MFA_REQUIRED
MFA_CHALLENGE_PASS != ROLE_ASSIGNMENT
EXTERNAL_IDENTITY != FALCON_ENTITLEMENT
```

---

## 3. سياسة العميل والـOwner

قرار الـOwner: المصادقة الإضافية تشمل **العميل والـProject Owner**.

الاتجاه الأمني المعتمد:

- MFA مطلوب للـProject Owner دائمًا.
- MFA مطلوب لحسابات العملاء عند تسجيل الدخول التشغيلي.
- إجراءات حساسة مثل تغيير MFA، تغيير البريد، ربط/فصل مزود هوية، أو تنفيذ Owner control تتطلب إعادة مصادقة/Step-Up حسب العقد authoritative.
- أي مسار بديل للدخول أو الاستعادة يجب ألا يكون أضعف من المسار الأساسي.

الـOwner يخضع لسياسة أشد ولا توجد bypass خاصة به.

```text
OWNER_ROLE -> MFA_REQUIRED
CUSTOMER_ROLE -> MFA_REQUIRED
OWNER_PRIVILEGE != MFA_BYPASS
ACCOUNT_RECOVERY != SECURITY_BYPASS
```

---

## 4. Authenticator portability

Falcon لا يعتمد على اسم تطبيق واحد. إذا استُخدم TOTP، يكون معيارياً بحيث يستطيع العميل استخدام تطبيق متوافق مثل:

- Google Authenticator
- Microsoft Authenticator
- أي TOTP authenticator متوافق يُعتمد لاحقًا

هذا يحافظ على قابلية الاستبدال ويمنع Vendor Lock-in.

```text
FALCON_DEPENDS_ON_MFA_CAPABILITY
FALCON_DOES_NOT_DEPEND_ON_AUTHENTICATOR_BRAND
```

---

## 5. اتجاه أقوى للأمان

TOTP مدعوم لأنه يحقق طلب الـOwner، لكن المعمارية لا تغلق الباب أمام عوامل أقوى مثل Passkeys/WebAuthn عندما تتم مراجعتها واعتمادها.

الأولوية الأمنية المستقبلية:

```text
PHISHING_RESISTANT_FACTOR_WHEN_AVAILABLE
> TOTP
> SINGLE_FACTOR_PASSWORD
```

لا يتم فرض عامل جديد أو ترقية سياسة الدخول بدون governance واختبارات مناسبة.

---

## 6. حدود الهوية والصلاحيات

Shared Web يعرض UX ويرسل طلبات المصادقة ويستهلك النتيجة authoritative فقط.

Shared Web لا:

- يصنع Falcon user identity من email أو Google/Microsoft profile وحده؛
- يمنح Project Owner role من claim غير موثق بالعقد؛
- يمنح FSATS subscription/entitlement لمجرد نجاح Google/Microsoft sign-in؛
- يخزن كلمات مرور مزودي الهوية؛
- يخزن TOTP secret أو recovery material في Web-owned reusable state/logs؛
- يعتبر نجاح OAuth/OIDC دليلاً على business authorization.

```text
OIDC_AUTHENTICATED != FALCON_OWNER
OIDC_AUTHENTICATED != FSATS_ENTITLED
MFA_PASSED != BUSINESS_AUTHORITY
WEB_SESSION != FOUNDATION_APPLICATION_AUTHORITY
```

---

## 7. Session and token security

التنفيذ النهائي يجب أن يستخدم session/token boundary authoritative ويتجنب وضع أسرار حساسة في browser persistence العادي.

المطلوب:

- TLS فقط.
- Authorization Code flow المناسب للتطبيق المعتمد، مع PKCE حيث ينطبق.
- التحقق من issuer/audience/signature/nonce/state والـredirect URI حسب المزود والعقد.
- جلسات قصيرة ومعقولة مع rotation/revocation.
- Step-Up / re-authentication للأفعال الحساسة.
- logout حقيقي للـFalcon session، وليس مجرد تغيير شاشة محلي.
- audit لأحداث الدخول والفشل وتغيير/استعادة MFA بدون تسجيل secrets.

---

## 8. Account linking

ربط حساب Falcon بمزود خارجي عملية governed مستقلة عن مجرد تسجيل الدخول.

مثال:

```text
Existing Falcon Account
  + verified Google identity
  -> explicit link flow
  -> authoritative confirmation
  -> linked identity
```

لا يجوز الربط التلقائي اعتمادًا على تطابق email وحده إذا لم يسمح العقد authoritative بذلك.

```text
EMAIL_MATCH != IDENTITY_LINK_AUTHORIZATION
```

---

## 9. Recovery

استعادة الحساب أو MFA يجب أن تكون قوية بما يكفي للحساب، خصوصًا الـOwner.

- recovery codes أو بدائل الاستعادة لا تعرض بعد الإنشاء إلا وفق سياسة واضحة.
- لا ترسل أسرار MFA في chat أو logs.
- تغيير عامل MFA يتطلب re-authentication ويفضل إشعارًا أمنيًا.
- Owner recovery يجب ألا يتحول إلى shortcut يضعف الحماية.

---

## 10. Current implementation boundary

يمكن لـShared Web الآن تنفيذ:

- Google/Microsoft sign-in buttons and UX.
- MFA challenge/enrollment/recovery presentation surfaces.
- auth adapter/port interfaces التي تفشل مغلقًا إذا لم توجد binding authoritative.
- tests تمنع اختراع الهوية/الدور/entitlement.

لكن **live external identity connectivity, authoritative session issuance, MFA secret custody, Falcon identity/role truth and production activation** يجب أن ترتبط بالجهة المالكة عبر governed contract/runtime boundary.

إذا لم توجد هذه القدرة authoritative حاليًا، يجب طلبها عبر FCR بدل بناء identity authority داخل Web.

---

## 11. External security evidence used for this direction

تمت مراجعة المصادر الرسمية الحالية قبل تثبيت هذا الاتجاه:

- Google Identity Services / Google OpenID Connect for web sign-in.
- Microsoft identity platform OpenID Connect and Microsoft Entra External ID guidance for customer-facing web applications.
- OWASP Authentication Cheat Sheet and Multifactor Authentication Cheat Sheet.

هذه المصادر Evidence وليست أعلى من Falcon Vision/Constitution/governance.

---

## 12. رقم الهاتف الإلزامي للتواصل في الحالات الطارئة

قرار الـProject Owner: كل مستخدم جديد يجب أن يسجل رقم هاتف ضمن onboarding بهدف التواصل معه في الحالات الطارئة والوقائع عالية الأولوية المرتبطة بحسابه أو استخدامه لـFalcon.

هذا الرقم هو **بيانات تواصل للعميل** وليس هوية تداول، وليس Broker Account identity، وليس بحد ذاته عامل مصادقة أو صلاحية.

```text
NEW_USER -> EMERGENCY_CONTACT_PHONE_REQUIRED
PHONE_NUMBER = CUSTOMER_CONTACT_DATA
PHONE_NUMBER != BROKER_ACCOUNT_IDENTITY
PHONE_NUMBER != FALCON_ROLE
PHONE_NUMBER != MFA_FACTOR
PHONE_NUMBER != BUSINESS_AUTHORITY
```

### UX المطلوب

- لا يكتمل onboarding للمستخدم الجديد قبل إدخال رقم هاتف صالح بصيغة دولية مناسبة.
- الواجهة تشرح بوضوح أن الغرض الأساسي هو **التواصل في الحالات الطارئة والتنبيهات عالية الأولوية**، وليس إرسال مواد تسويقية افتراضيًا.
- يجب عرض وتحديث رقم الهاتف من إعدادات الحساب عبر مسار واضح.
- تغيير رقم الهاتف لاحقًا يحتاج مسارًا governed ومتوافقًا مع سياسة الهوية/الجلسة المعتمدة وقت التنفيذ.
- إذا كانت خدمة OTP مؤجلة، فإن وجود رقم الهاتف **لا يعني** أن الرقم verified عبر OTP حاليًا. يجب إبقاء `PROVIDED` و`VERIFIED` حالتين منفصلتين.
- لا يتم اختراع حالة `VERIFIED` لمجرد إدخال الرقم أو حفظه.

```text
PHONE_PROVIDED != PHONE_VERIFIED
CONTACTABLE != AUTHENTICATED
EMERGENCY_CONTACT_PERMISSION != MARKETING_CONSENT
```

### العلاقة مع الحوادث

Shared Web يملك customer/contact mapping وواجهة التواصل، بينما Trading/Guardian يملكان business/incident semantics. لذلك استخدام رقم الهاتف للطوارئ لا يسمح للويب باختراع شدة الحادث أو ضرورة الاتصال من نفسه؛ يتم الاتصال فقط عندما توجد حالة/سياسة authoritative تستدعي ذلك.

```text
APPLICATION_INCIDENT_SEMANTICS != CUSTOMER_CONTACT_DATA
CONTACT_CHANNEL_AVAILABLE != INCIDENT_RESOLVED
NOTIFICATION_DELIVERED != USER_ACKNOWLEDGED
```

### الخصوصية والحد الأدنى من البيانات

- يجمع Falcon الرقم لأنه مطلوب لغرض تشغيلي محدد: التواصل الطارئ وحالات الأولوية العالية.
- لا يُستخدم الرقم تلقائيًا للتسويق إلا بموافقة منفصلة إذا تم اعتماد تسويق هاتفي مستقبلًا.
- لا يظهر الرقم في logs أو surfaces غير لازمة.
- لا يُرسل إلى Application/Guardian كبيانات business إلا عبر boundary مصرح به عندما توجد حاجة فعلية للتواصل.

---

هذا القرار يوسع Web-owned onboarding/contact UX ويثبت أن رقم الهاتف مطلوب للمستخدم الجديد لأغراض التواصل الطارئ. لا يحول رقم الهاتف إلى هوية Falcon أو عامل MFA، ولا يفعّل OTP المؤجل، ولا يمنح Web سلطة business/incident من نفسه.
