# Shared Falcon Web - سلم انتباه التنبيهات وتجربة الإشعارات

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يوثق قرارات UX القابلة للعكس والمملوكة للـShared Web والمبنية على دراسة أنماط التنبيهات المألوفة في أنظمة تصميم واسعة الاستخدام، مع الحفاظ الكامل على حدود Falcon الحالية.

لا يمنح هذا الملف implementation/runtime/messaging authority، ولا يعرّف business semantics مملوكة للـApplication أو Foundation.

---

## 1. الهدف

الهدف هو جعل التنبيهات:

- سهلة الفهم خلال ثوانٍ.
- مألوفة للمستخدم بدل اختراع سلوك غريب جديد.
- متناسبة في الإزعاج مع أهمية الرسالة.
- واضحة بصريًا بدون ضوضاء مستمرة.
- إنسانية في اللغة.
- قابلة للرجوع إليها من مركز التنبيهات أو الأرشيف حسب القواعد المعتمدة.
- غير مضللة بخصوص الحقيقة أو الصلاحيات أو حالة التنفيذ.

المبدأ الأساسي:

```text
ATTENTION LEVEL SHOULD MATCH ACTUAL IMPORTANCE
```

وليس:

```text
EVERY NOTIFICATION = POPUP
```

## 2. Notification Attention Ladder

يعتمد Shared Web سلم انتباه من أربع درجات UX. هذا السلم لا يصنع درجة الخطورة من نفسه، بل يستهلك classification موثوقًا من الجهة المالكة عندما يكون له معنى domain/security.

### Level 1 - Quiet / Informational

للمعلومات التي لا تحتاج مقاطعة المستخدم.

السلوك الافتراضي:
- تدخل في Notification Center الخاص بالـApplication.
- تزيد unread count إذا كانت غير مقروءة.
- لا Popup تلقائي.
- لا صوت/حركة لافتة داخل الويب لمجرد أنها وصلت.
- يمكن أن تظهر كعنصر جديد داخل القائمة بهدوء.

أمثلة UX عامة:
- تحديث معلوماتي.
- خبر عام.
- تذكير غير عاجل.
- حملة/عرض عام وفق القواعد المعتمدة.

### Level 2 - Immediate Feedback

لنتيجة مباشرة من فعل قام به المستخدم للتو، مثل حفظ إعداد أو تنفيذ عملية UI بنجاح أو فشل غير حرج.

السلوك الافتراضي:
- Toast / Flag خفيف وقصير.
- لا Modal.
- لا يحتاج من المستخدم إغلاقًا يدويًا إذا كانت الرسالة مجرد تأكيد بسيط.
- يبقى المسار الأساسي للمستخدم بدون تعطيل.
- إذا كان التنبيه نفسه يحتاج أن يبقى قابلًا للرجوع إليه، يحتفظ Notification Center بنسخته المناسبة حسب سياسة النوع، ولا يعتمد على الـToast وحده.

أمثلة:
- `تم حفظ الإعدادات.`
- `تعذر حفظ التغيير. حاول مرة أخرى.`

### Level 3 - Contextual Important

لمعلومة مهمة مرتبطة بجزء معين من الشاشة أو تحتاج انتباهًا واضحًا، لكنها لا تستحق قطع كامل للسياق.

السلوك الافتراضي:
- Inline / Section message أو Banner داخل السياق المناسب.
- يبقى ظاهرًا طالما ما زالت المعلومة ذات صلة أو وفق حالة المصدر.
- إذا كان هناك إجراء، يكون واضحًا وقريبًا من الرسالة.
- لا يستخدم Modal إلا إذا أصبح القرار نفسه يحتاج تفاعلًا حتميًا.

أمثلة UX عامة:
- مشكلة في جزء محدد من الصفحة.
- حالة degraded لمكوّن ظاهر للمستخدم.
- معلومة مؤثرة على ما يراه حاليًا.

### Level 4 - Interruptive / Action Required

محجوز للحالات التي تستحق قطع السياق فعلًا.

السلوك الافتراضي:
- Popup / Dialog واضح.
- عنوان قصير يصف ما حدث، وليس عنوانًا عامًا مثل `خطأ`.
- شرح قصير جدًا عند الحاجة.
- الـAction الأساسي واضح بصياغة نتيجة بشرية.
- عدد الأزرار يبقى محدودًا قدر الإمكان.
- لا يستخدم لمجرد عرض معلومة يمكن قراءتها لاحقًا.

هذا المستوى لا يحق للـShared Web أن يطبقه على Guardian أو business-domain state من تلقاء نفسه إذا كانت `action-required` أو `urgency` غير معرفة من الجهة المالكة.

FCR-0095 يبقى المرجع المفتوح لجزء Guardian user-targeted urgent/action-required semantics.

## 3. قاعدة تقليل المقاطعة

اعتمادًا على مبدأ familiarity + interruption proportionality:

```text
INFORMATION -> CENTER / INLINE
USER ACTION FEEDBACK -> TOAST
IMPORTANT CONTEXT -> INLINE / BANNER
MUST ACT NOW -> DIALOG
```

الـModal ليس badge أكبر. هو مقاطعة للسياق، لذلك استخدامه يجب أن يظل نادرًا حتى يحتفظ بقيمته النفسية.

إذا كل شيء صرخ، المستخدم يتعلم تجاهل الصراخ.

---

## 4. صياغة النص البشري

كل user-facing notification copy يجب أن يكون:

- قصيرًا.
- مباشرًا.
- طبيعيًا.
- يشرح ما حدث أو ما يحتاجه المستخدم بدون jargon داخلي.
- لا يعرض IDs أو enums أو event codes لمجرد أنها موجودة داخليًا.
- لا يستخدم عنوانًا فارغ المعنى مثل `Error` إذا يمكن قول المشكلة نفسها.

أمثلة أفضل:

```text
تم حفظ الإعدادات.
```

بدل:

```text
SETTINGS_UPDATE_SUCCESS
```

ومثال:

```text
تعذر الاتصال بالسوق الآن.
```

بدل:

```text
MARKET_CONNECTION_ERROR_42
```

إذا كانت المعلومة حساسة، لا تُكشف في preview العام أكثر من اللازم.

## 5. بنية العنصر داخل Notification Center

يستخدم العنصر نمطًا مألوفًا وبسيطًا:

1. أيقونة/علامة نوع مفهومة بصريًا عندما تضيف قيمة.
2. عنوان قصير وواضح.
3. سطر ملخص واحد أو اثنان عند الحاجة.
4. وقت نسبي قريب مثل `قبل 5 دقائق`، مع إمكانية إظهار التاريخ الكامل عند الحاجة في التفاصيل.
5. حالة unread مرئية بوضوح بدون جعل البطاقة كلها صاخبة.
6. مصدر الـApplication يكون واضحًا داخل مركز ذلك الـApplication أو عند الحاجة في السطح المشترك.

لا تستخدم زخرفة أو ألوان كثيرة لجذب الانتباه. اللون والحركة يخدمان المعنى، لا ينافسان المحتوى.

## 6. Unread behavior

يحافظ Shared Web على القواعد المعتمدة سابقًا:

```text
OPEN NOTIFICATION = READ
```

وبالتالي:
- unread badge ينخفض فور فتح التنبيه.
- الـbadge يمثل unread count فقط.
- لا يستخدم لأسعار أو أرقام أخرى.
- لا يبقى رقم قديم بعد أن يقرأ المستخدم العناصر.

على Falcon Home يبقى السلوك المعتمد:
- Bell مألوف.
- دائرة صغيرة حمراء.
- الرقم = مجموع unread المسموح للمستخدم رؤيته عبر Applications التي يملك وصولًا إليها.
- لا preview نصي على Falcon Home.

---

## 7. Bell quick list

عند الضغط على الجرس:

- تظهر قائمة مختصرة وخفيفة.
- الأحدث أولًا في قائمة الجرس النشطة كاختيار UX بديهي، ما لم توجد قاعدة نوعية أقوى.
- يظهر عدد محدود مناسب من أحدث العناصر بدل تحويل dropdown إلى صفحة كاملة.
- يوجد وصول واضح إلى مركز التنبيهات الخاص بالـApplication المعني عندما يحتاج المستخدم الاستعراض الكامل.
- الضغط على عنصر يفتح محتواه في Popup/Dialog على نفس الصفحة وفق القرار السابق.

هذه القائمة quick-access وليست مركزًا موحدًا يعيد ملكية التنبيهات من Applications.

---

## 8. Toast / Flag behavior

للرسائل القصيرة الناتجة مباشرة عن user action:

- تظهر في مكان ثابت ومتوقع داخل الواجهة.
- مدة ظهور قصيرة ومعقولة للمعلومة البسيطة.
- لا تغطي المحتوى الأساسي أكثر من اللازم.
- الرسائل المتعددة تتكدس بترتيب واضح بدل أن تظهر فوق بعضها عشوائيًا.
- الأحدث يكون أوضح بصريًا.
- الرسالة لا تتجاوز تقريبًا بضعة أسطر؛ إذا احتاجت شرحًا طويلًا فهي ليست Toast.

إذا كان الـToast يحتوي Action يحتاج وقتًا من المستخدم، لا يختفي بسرعة قبل أن يتمكن من فهمه والتفاعل معه.

---

## 9. Banner / Inline behavior

يستخدم Banner أو Inline message عندما تكون الرسالة مهمة للسياق وليست بحاجة لقطع كامل للعمل.

أمثلة:
- مشكلة اتصال تؤثر على الصفحة الحالية.
- جزء من البيانات غير متاح.
- حالة مهمة تخص قسمًا محددًا.

القاعدة:

```text
LOCAL PROBLEM -> LOCAL MESSAGE
GLOBAL SERIOUS PROBLEM -> PROMINENT GLOBAL SURFACE
```

لا نرسل المستخدم إلى Notification Center كي يفهم مشكلة ظاهرة أمامه الآن إذا يمكن شرحها بجانب الشيء المتأثر نفسه.

---

## 10. Dialog behavior

عندما يكون Dialog مبررًا:

- عنوانه يصف الحالة مباشرة.
- النص الإضافي لا يكرر العنوان.
- الـPrimary Action يكون فعلًا واضح النتيجة.
- Secondary Action عند الحاجة فقط.
- لا نضع قائمة أزرار طويلة.
- لا نشرح في paragraph ماذا يفعل كل زر إذا كانت تسمية الزر نفسها واضحة.
- destructive/irreversible actions تظل تحت قواعد التأكيد المعتمدة الخاصة بها ولا تُبسط باسم UX convenience.

## 11. Motion and visual attention

الحركة تستخدم كإشارة، لا كزينة مستمرة.

اعتماد UX:
- دخول Toast أو القائمة بحركة قصيرة ناعمة.
- لا blinking مستمر للتنبيهات العادية.
- لا اهتزاز بصري متكرر للجرس لجذب المستخدم بالقوة.
- unread badge يتحدث بهدوء.
- transition من unread إلى read واضح لكن غير استعراضي.
- critical/action-required يمكن أن يحصل على prominence أعلى فقط إذا كانت حالته authoritative.

الهدف النفسي:

```text
NOTICE ME WHEN I MATTER
DO NOT TRAIN ME TO IGNORE YOU
```

## 12. تجنب Notification Fatigue

يعتمد Shared Web هذه القواعد:

- لا نكرر نفس التنبيه عدة مرات داخل الواجهة لمجرد أن المستخدم لم يفتحه بعد، إلا إذا semantics المالك تفرض حدثًا جديدًا مستقلًا.
- لا نحول marketing/general info إلى urgency عالية.
- لا نستخدم Popup للمعلومات العامة.
- لا نستخدم اللون الأحمر كزخرفة عامة.
- لا نجعل كل success confirmation persistent.
- نوفر للمستخدم مركزًا يمكنه الرجوع إليه بدل إجباره على التقاط كل رسالة لحظة ظهورها.

---

## 13. Accessibility and control

- لا يعتمد المعنى على اللون وحده.
- حالات focus/hover/pressed تكون واضحة ومتسقة.
- الأزرار وأهداف النقر مألوفة وسهلة.
- الرسائل المهمة يمكن الوصول إليها بلوحة المفاتيح.
- Actionable notification التي تأخذ focus تستخدم فقط عندما التفاعل فعليًا مطلوب، لأن خطف focus نفسه مقاطعة.
- لا نعتمد على motion أو sound وحدهما لتوصيل معنى أساسي.

---

## 14. العلاقة مع القواعد السابقة

هذه الدراسة لا تلغي القرارات السابقة، بل تنظّمها:

- Per-Application Notification Center + Archive يبقيان كما تم اعتمادهما.
- Falcon Home bell = unread count فقط.
- Bell dropdown = compact titles/list.
- فتح التنبيه = Read.
- `×` للتنبيه العادي = Archive.
- Active critical/security/emergency يظل في active center حتى authoritative resolution، و`×` أثناء Active يغلق العرض فقط.
- resolved critical ينتقل تلقائيًا للأرشيف ويبقى وفق قاعدة الاحتفاظ الدائم المعتمدة.
- user-facing language تبقى بشرية.
- campaign/marketing consent rules تبقى منفصلة ومحفوظة.
- Guardian personal urgent/action-required UX لا يُجمّد قبل حسم FCR-0095.

## 15. مصادر الدراسة

تمت مراجعة مبادئ حالية من أنظمة تصميم واسعة الاستخدام، خصوصًا:

- Apple Human Interface Guidelines: Notifications, Alerts, Managing Notifications, Feedback, Design Principles.
- IBM Carbon Design System: Notification usage and notification pattern.
- Atlassian Design System: Flag, Designing Messages, Info Messages, Badge.
- Material Design 3: interaction states, adaptive/canonical layout principles, familiarity/expressive-but-usable interaction direction.

المشترك بينها الذي تبناه هذا الملف:

```text
FAMILIARITY
+ CONCISE HUMAN COPY
+ PROPORTIONAL INTERRUPTION
+ CLEAR FEEDBACK
+ ACCESSIBILITY
+ USER CONTROL
= BETTER NOTIFICATION UX
```

## 16. حدود القرار الذاتي للـShared Web

يمكن للـShared Web اتخاذ وتحسين القرارات البديهية القابلة للعكس مثل:
- placement;
- spacing;
- animation subtlety;
- list density;
- relative timestamps;
- toast duration within normal UX bounds;
- clear/reset behaviors;
- keyboard/focus ergonomics;
- conventional icons and ordering;

بدون الرجوع للـOwner لكل نقطة.

لكن لا يتم الاجتهاد ذاتيًا في:
- business meaning;
- who is authorized;
- who is targeted when the owning Application has not defined it;
- trading action semantics;
- subscription/money/offer policy;
- consent/privacy/security policy;
- retention/deletion policy;
- irreversible actions;
- Foundation/Application authority;
- criticality/action-required classification owned by another workstream.
