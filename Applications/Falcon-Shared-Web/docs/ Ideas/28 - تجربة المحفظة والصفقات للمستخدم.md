# Shared Falcon Web - تجربة المحفظة والصفقات للمستخدم

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يسجل قرارات الـOwner الحالية الخاصة بعرض المحفظة والصفقات للمستخدم العادي داخل FSATS من منظور Shared Web فقط، ويضيف اتجاه UX مبنيًا على مراجعة أنماط منصات تداول حالية ومعايير Web accessibility. لا يمنح implementation/runtime/trading authority ولا يغير ملكية الحقيقة داخل FSATS أو broker/provider contracts.

---

## 1. إخفاء Broker Account كتعقيد داخلي عن تجربة المستخدم

قرار الـOwner:

Shared Web لا يجعل `Broker Account` كيانًا مرئيًا أو محورًا في تجربة المستخدم العادي لمجرد أن FSATS يستخدم broker-account identity داخليًا في بعض العقود أو الحوادث.

المهم للمستخدم هو أن يرى بياناته وحالته وصفقاته المرتبطة بحسابه وتجربته داخل Falcon بصورة مفهومة، بينما تبقى هوية broker/account الداخلية شأنًا تشغيليًا/عقديًا عند الحاجة.

```text
INTERNAL BROKER-ACCOUNT IDENTITY
!=
MANDATORY USER-FACING NAVIGATION CONCEPT

USER-FACING PORTFOLIO VIEW
-> PRESENT AUTHORIZED USER DATA / POSITIONS / TRADES / RESULTS
-> DO NOT EXPOSE INTERNAL ACCOUNT ROUTING COMPLEXITY WITHOUT A UX NEED
```

هذا لا يلغي العقود التي تحتاج `BrokerId + BrokerAccountId` داخليًا، ولا يغير Application ownership؛ هو قرار presentation فقط.

---

## 2. المستخدم العادي يرى تجربته الحية فقط

قرار الـOwner:

المستخدم العادي لا يتم تقديمه له كـSimulator user ولا يرى Simulator mode كجزء من تجربته اليومية.

الواجهة العادية تعرض للمستخدم الحالة والبيانات والصفقات التي توفرها له المسارات المصرح بها لحسابه الحالي، مع عرض current/live truth كما تصل من أصحابها authoritative.

```text
REGULAR USER UX = LIVE/CURRENT USER EXPERIENCE
REGULAR USER UX != SIMULATOR CONSOLE
```

Shared Web لا يقرر من نفسه نوع runtime أو broker/provider path ولا يحوله إلى business truth. دوره عرض النتيجة authoritative التي تصل له.

---

## 3. Simulator للـOwner فقط

قرار الـOwner:

Simulator وما يتعلق بعرضه التشغيلي أو المقارنات الخاصة به يكون ضمن تجربة الـProject Owner، وليس ضمن تجربة المستخدم العادي.

```text
SIMULATOR PRESENTATION = OWNER-ONLY UX
SIMULATOR PRESENTATION != REGULAR USER PORTFOLIO UX
```

أي تفاصيل عن simulator truth، controls، comparison أو authority تبقى خاضعة لعقود Application/Foundation المناسبة ولا يملك Web اختراعها.

---

## 4. Research basis غير الملزم معماريًا

تمت مراجعة أنماط حالية من منصات/مراجع خارجية لفهم أفضل UX patterns، بدون اعتبارها Falcon authority:

- TradingView: فصل `Positions`, `Orders`, `History` وربط المراكز/الأوامر بالشارت عند الحاجة.
- TradingView Account Manager: account summary سريع ثم tabs للنشاط التفصيلي.
- Interactive Brokers PortfolioAnalyst: فصل snapshot الحساب عن performance / allocation / activity والتحليل الأعمق.
- Alpaca Trading API documentation: account state, positions, order lifecycle, real-time trade updates، وتمييز حالات `new`, `partial_fill`, `fill`, `canceled`, `rejected` وغيرها.
- W3C WCAG 2.2 / WAI-ARIA: reflow، عدم الاعتماد على اللون وحده، وإتاحة status updates بصورة مناسبة.

هذه المصادر تلهم presentation فقط ولا تمنح أي contract/business authority داخل Falcon.

## 5. الهيكل المقترح لتجربة المستخدم

أفضل اتجاه لفالكون هو عدم بناء "شاشة تداول ضخمة" واحدة، بل توزيع التجربة إلى أربع طبقات مترابطة:

```text
FSATS HOME
  -> QUICK USER FINANCIAL SNAPSHOT
  -> MARKETS / OPPORTUNITIES
  -> OPEN POSITIONS PREVIEW
  -> RECENT ACTIVITY PREVIEW

PORTFOLIO
  -> ACCOUNT SUMMARY
  -> POSITIONS
  -> PERFORMANCE
  -> ALLOCATION / EXPOSURE WHEN AUTHORITATIVELY AVAILABLE

ACTIVITY
  -> ACTIVE ORDERS WHEN APPLICABLE
  -> EXECUTED TRADES
  -> ORDER / TRADE HISTORY

ASSET DETAIL
  -> CHART + FALCON SUMMARY
  -> MY POSITION CARD WHEN THE USER HOLDS THE ASSET
  -> RELATED RECENT TRADES
```

هذا يحافظ على الصفحة الرئيسية خفيفة، ويعطي المستخدم drill-down واضح عند الحاجة.

## 6. FSATS Home - الملخص السريع

في أعلى FSATS Home يظهر شريط/مجموعة بطاقات مختصرة فقط عندما ترجع القيم authoritative:

- `Portfolio Value` أو المعنى المكافئ من Application contract.
- `Today P/L` عندما تكون دلالته متاحة authoritative.
- `Total / Unrealized P/L` أو metric مكافئ إذا كان معرّفًا من المصدر.
- `Available Funds / Buying Power` إذا كان من ضمن customer-facing semantics.

لا نعرض عشرات المقاييس في Home.

أسفلها:

- أهم المراكز المفتوحة.
- آخر الصفقات المكتملة.
- مدخل واضح إلى `View Portfolio` و`View Activity`.

```text
HOME = ORIENTATION
PORTFOLIO = FINANCIAL DETAIL
ACTIVITY = EXECUTION HISTORY
```

## 7. Portfolio Page

### 7.1 Account Summary

Header واضح يحتوي القيم الأساسية فقط، بدون إظهار BrokerId أو Broker Account Number كجزء افتراضي من UX.

ترتيب مرشح:

```text
Portfolio Value
Today P/L
Total P/L
Available Funds / Buying Power
```

إذا بعض هذه القيم غير موجودة في العقد، لا يحسبها Web أو يخترع بديلًا.

### 7.2 Positions

Desktop table مرشح:

```text
Symbol / Asset
Quantity
Average Entry
Current Price
Market Value
Today Change
Unrealized P/L
Total Return or equivalent authoritative metric
```

- السطر كامل قابل للنقر ويفتح Asset Detail.
- ترتيب وفرز الأعمدة UX-owned عندما لا يغير المعنى.
- المستخدم يستطيع البحث/filter داخل مراكزه.
- القيم الصاعدة/الهابطة تستخدم لون + sign/icon/text، وليس اللون وحده.

### 7.3 Position detail quick drawer

بدل إجبار المستخدم على مغادرة Portfolio لكل معلومة، يمكن فتح drawer سريع عند الضغط على المركز يعرض:

- الكمية.
- Average Entry.
- Current Price.
- Market Value.
- P/L.
- آخر حركة/صفقة ذات صلة إن توفرت.
- `Open Full Asset Analysis`.
- `Ask Falcon about this position`.

لا يظهر broker routing detail للمستخدم العادي.

## 9. Activity Page

أفضل فصل هو tabs واضحة:

```text
Active
Trades
History
```

تظهر فقط الأقسام التي لها معنى فعلي في العقد النهائي.

### 9.1 Active

للأوامر/الطلبات التي لم تصل إلى terminal state عندما يسمح Application بعرضها.

العرض المرشح:

- Asset.
- Side عندما يكون customer-facing.
- Quantity.
- Order type إذا كان جزءًا من الحقيقة المعروضة.
- Submitted/Created time.
- Current authoritative status.
- Filled quantity إذا كان هناك partial fill.

### 9.2 Trades

للـexecutions التي حدثت فعلًا:

- Asset.
- Buy/Sell أو business-equivalent authoritative value.
- Quantity.
- Execution price.
- Execution time.
- Resulting P/L إذا كان contract يوفره بهذا المستوى.

### 9.3 History

Timeline كامل للحالات المنتهية والمهمة:

- Filled.
- Canceled.
- Rejected.
- Expired.
- Replaced أو equivalent عندما يكون موجودًا.

ويظل الفصل التالي إلزاميًا:

```text
ORDER REQUESTED != ORDER ACCEPTED
ORDER ACCEPTED != PARTIALLY FILLED
PARTIALLY FILLED != FILLED
CANCEL REQUESTED != CANCELED
REJECTED != CANCELED
```

Web لا يبسط هذه الحالات إلى نجاح/فشل فقط إذا كان المصدر يميز بينها.

## 10. Live/current update behavior

التحديثات الحية يجب أن تكون هادئة ولا تجعل الأرقام تقفز بصريًا كآلة قمار.

الاتجاه:

- تحديث القيم في مكانها.
- micro-highlight قصير عند تغير قيمة مهمة، بدون animation مزعج.
- لا نعتمد على الأخضر/الأحمر وحدهما؛ sign + text/icon عند الحاجة.
- high-frequency price ticks لا تولد screen-reader announcement لكل tick.
- status changes المهمة مثل `Filled`, `Rejected`, `Connection degraded` تستخدم status semantics مناسبة.
- إذا truth أصبحت stale/unknown/unavailable، نظهر ذلك كحالة تشغيلية فعلية فقط.

```text
LIVE UPDATE != VISUAL NOISE
PRICE TICK != USER ALERT
STATE CHANGE MAY REQUIRE STATUS MESSAGE
```

## 11. Performance Page / Section

الـPerformance ليس المكان المناسب لإغراق المستخدم بعشرات ratios افتراضيًا.

الواجهة الأساسية المرشحة:

1. Portfolio value / performance curve.
2. فترة زمنية: `1D / 1W / 1M / 3M / 1Y / ALL` أو الفترات التي يدعمها المصدر.
3. P/L summary للمدة المختارة.
4. Top contributors / detractors إذا كان Application يقدم attribution authoritative.
5. Allocation / exposure إذا كان Application يقدمها.
6. Trade activity summary.

Advanced metrics مثل Sharpe/Sortino/Drawdown وغيرها لا تعرض لمجرد أنها شائعة؛ تظهر فقط إذا كانت جزءًا من Falcon/Application product semantics ومفيدة للمستخدم.

## 13. Loading / stale / degraded / unavailable

الحالة الطبيعية لا تعرض warnings.

لكن إذا المصدر authoritative أبلغ عن حالة تشغيلية:

- Loading -> skeleton/placeholders بدون أرقام مزيفة.
- Stale -> label واضح مع آخر وقت مؤكد إذا توفر.
- Unavailable -> لا نعرض آخر قيمة كأنها current.
- Partial -> نظهر المتاح ونوضح أن الحالة جزئية فقط إذا قال المصدر ذلك.
- Reconnecting -> لا يعني أن الحقيقة أصبحت current بعد الاتصال وحده.

```text
LAST KNOWN VALUE != CURRENT VALUE
RECONNECTED != DATA RECONCILED
NO SOURCE VALUE != ZERO
```

## 14. Responsive / Mobile

Mobile لا يكون نسخة desktop مضغوطة.

الاتجاه المرشح:

- Bottom navigation: `Home / Markets / Portfolio / Activity / AI` أو أقرب final IA مع الحفاظ على App shell.
- Portfolio summary كبطاقات أفقية/عمودية قصيرة.
- Positions تتحول من table إلى compact cards أو prioritized columns.
- التفاصيل الثانوية تفتح drawer/sheet.
- الشارت يحتفظ بالسلوك ثنائي الأبعاد عندما يكون ضروريًا، بينما بقية المحتوى يعيد reflow.
- الإجراءات/روابط drill-down تكون ذات touch targets واضحة.

هدفنا WCAG 2.2 AA كاتجاه جودة، مع reflow وعدم فقدان الوظائف على الشاشات الصغيرة.

---

## 15. Accessibility

- اللون لا يكون وحده دلالة الربح/الخسارة أو status.
- keyboard navigation لكل tabs/tables/drawers.
- focus واضح وغير محجوب.
- semantic headings/labels.
- status updates المهمة تستخدم accessible live/status pattern بدون إزعاج مستمر.
- charts تحتاج textual summary/accessible alternative للمعلومة الأساسية التي يعتمد عليها المستخدم.
- الأرقام المالية تعرض sign/currency/unit بوضوح.

---

## 16. ما لا يظهر للمستخدم العادي

بناءً على قرار الـOwner الحالي:

```text
NO SIMULATOR CONSOLE
NO PAPER/SHADOW/TINY-LIVE OPERATIONAL MODE SELECTOR
NO BROKER ACCOUNT ROUTING UI BY DEFAULT
NO PROVIDER ROUTING DETAILS
NO INTERNAL FALCON CONTROL-PLANE DETAIL
```

المستخدم يرى تجربته وبياناته ونتائج صفقاته. التفاصيل التشغيلية الداخلية تبقى عند أصحابها، والـSimulator ضمن Owner experience.

---

## 17. حدود الملكية

```text
APPLICATION / GOVERNED SOURCE = ACCOUNT / POSITION / ORDER / TRADE / PERFORMANCE TRUTH OWNER
SHARED WEB = PRESENTATION / NAVIGATION / RESPONSIVE / ACCESSIBILITY OWNER
WEB DISPLAY != PORTFOLIO CALCULATION AUTHORITY
WEB DISPLAY != EXECUTION AUTHORITY
WEB DISPLAY != BROKER ACCOUNT BUSINESS OWNER
```

قبل implementation-ready binding، يجب التأكد أن Application يملك customer-facing projections الكافية للمحفظة والمراكز والصفقات/order lifecycle والأداء. إذا لم تكن موجودة، تُطلب عبر FCR بدل أن يبني Web business semantics من نفسه.

هذه المرحلة Planning/Discussion فقط.
