# Shared Falcon Web - بوابة الحوار والـAI والموافقات

**Status:** `DRAFT / DISCUSSION ONLY`

هذه الوثيقة تشرح تجربة الحوار الطبيعية بين المستخدم أو الـOwner وبين Falcon Applications، مع الحفاظ على الفصل بين سهولة الكلام وبين business authority الفعلية.

---

## 1. المبدأ الأساسي

كل مستخدم داخل Falcon Application يجب أن يستطيع التعامل مع الـApplication بلغة طبيعية من خلال AI conversational interface بدل إجباره على معرفة أوامر تقنية أو نماذج معقدة للحصول على معلومة أو تحليل.

الفكرة:

```text
USER TALKS NATURALLY
        ↓
AI UNDERSTANDS INTENT
        ↓
AI STRUCTURES THE REQUEST
        ↓
GOVERNED REQUEST TO THE TARGET APPLICATION
        ↓
APPLICATION RETURNS AUTHORITATIVE DATA / RESULT
        ↓
AI EXPLAINS AND PRESENTS IT CLEARLY
        ↓
USER CONTINUES THE CONVERSATION
```

الـAI يجعل Falcon سهل الاستخدام، لكنه لا يصبح مالكًا لبيانات الـApplication أو business truth أو authority.

---

## 2. User Conversational Experience

المستخدم العادي لا يُفترض أن يعرف كيف يكتب أوامر مثل:

```text
GET SYMBOL=AAPL PERIOD=90D INDICATORS=...
```

ولا يحتاج أن يعرف أي internal API أو route أو query syntax.

بدل ذلك يستطيع أن يقول مثلًا:

```text
حلللي سهم Apple، وهل وضعه مناسب حاليًا؟
```

أو:

```text
ليش السهم نازل اليوم؟
```

أو:

```text
قارنلي هالسهم مع Microsoft بطريقة بسيطة.
```

أو يكمل الحوار:

```text
طيب ركزلي على المخاطر.
```

ثم:

```text
اشرحلي النتيجة أبسط.
```

الـAI يحافظ على سياق المحادثة المسموح به حتى لا يضطر المستخدم لإعادة كتابة الطلب من الصفر في كل مرة.

---

## 3. دور الـAI

الـAI في Shared Web / Application-facing experience يقوم من منظور UX بما يلي:

1. يفهم كلام المستخدم الطبيعي.
2. يحدد ما الذي يطلبه المستخدم فعليًا.
3. يطلب clarification فقط عندما يكون الغموض مؤثرًا فعلًا.
4. يحول الطلب إلى structured intent مناسب لإرساله للـApplication الصحيح من خلال العقد المعتمد مستقبلًا.
5. لا يخترع بيانات السوق أو business results من عنده.
6. يستقبل البيانات/التحليل/النتيجة authoritative من الـApplication أو من واجهته المصرح بها.
7. يعرض النتيجة للمستخدم بشكل واضح، مختصر أو مفصل حسب طلبه.
8. يسمح بأسئلة follow-up طبيعية فوق نفس السياق.

قاعدة:

```text
AI INTERPRETATION != APPLICATION BUSINESS TRUTH
AI EXPLANATION != SOURCE DATA OWNERSHIP
```

---

## 4. FSATS Advisory / Analysis Example

تجربة المستخدم المرشحة في FSATS:

```text
User:
حلللي سهم معين
        ↓
AI understands:
- target instrument
- requested type of analysis
- relevant conversation context
        ↓
AI sends governed information/analysis request
        ↓
FSATS obtains/uses its authoritative operational data and domain logic
        ↓
FSATS returns data / analysis / confidence / limitations as applicable
        ↓
AI presents:
- النتيجة
- الأسباب المهمة
- المخاطر
- الأشياء غير المؤكدة
- التفاصيل الإضافية عند الطلب
```

المستخدم لا يحتاج إلى API credentials خاصة به من أجل advisory, consultation, analysis, recommendations أو عرض المعلومات والنتائج.

User-supplied API/broker credentials تخص مسار Automated Trading فقط حسب اتجاه الـOwner الحالي، وهذا قيد إعادة المزامنة مع FSATS عبر FCR-0081.

---

## 5. Conversation Should Be Progressive

الهدف ليس سؤالًا واحدًا ثم نتيجة جامدة.

المحادثة تكون قابلة للاستمرار، مثل:

```text
User: حلللي AAPL
AI: يعرض النتيجة

User: طيب شو أكبر خطر؟
AI: يجيب بناءً على نفس التحليل والسياق

User: قارنه مع MSFT
AI: يطلب/يستقبل المقارنة اللازمة ويعرضها

User: اشرحلي الفرق كأني مش خبير تداول
AI: يعيد تقديم النتيجة بلغة أبسط
```

لكن أي بيانات جديدة أو business conclusion جديدة يجب أن تبقى مبنية على authoritative Application information، وليس على افتراض أن سياق المحادثة القديم ما زال صحيحًا إلى الأبد.

`CONVERSATION CONTEXT != DATA FRESHNESS`

---

## 6. Advisory Is Different from Execution

سهولة الشات لا تلغي حدود السلطة.

مثال:

```text
User: شو رأيك أشتري Apple؟
```

هذا طلب تحليل/استشارة.

أما:

```text
User: اشتريلي Apple الآن
```

فهذا قد يكون طلب تنفيذ، وبالتالي يدخل في مسار مختلف تمامًا إذا كان المستخدم مخولًا وAutomated Trading مفعّلًا والعقود التنفيذية موجودة.

Mandatory distinction:

```text
ASK FOR ANALYSIS
!=
REQUEST EXECUTION
!=
EXECUTION AUTHORIZED
!=
EXECUTION COMPLETED
```

الـAI يجب أن يعرف الفرق في تجربة الاستخدام، والـWeb لا يحول الاستشارة إلى تنفيذ لمجرد أن الجملة تبدو قريبة منه.

---

## 7. Ordinary User vs Project Owner

نفس فكرة المحادثة الطبيعية قد تظهر للمستخدم والـOwner، لكن صلاحية الكلام ليست واحدة.

### Ordinary User

يستخدم الـAI ضمن ما تسمح به صلاحياته، مثل:

- طلب معلومات.
- طلب تحليل.
- طلب مقارنة.
- طلب تفسير.
- طلب توصيات/استشارات عندما تكون هذه الوظيفة متاحة.
- لاحقًا طلب actions فقط إذا كان مخولًا لها فعلًا.

### Project Owner

الـOwner يستطيع أيضًا استخدام Conversational Gateway لطلبات إدارية/حوكمية/تطويرية تقع ضمن سلطته.

مثال Owner:

```text
أضيف السوق السعودي
```

لكن حتى مع الـOwner، الكلام الطبيعي لا يدمج مراحل authority المختلفة ببعض.

```text
OWNER REQUEST
!=
IMPLEMENTATION AUTHORITY
!=
TEST AUTHORITY
!=
PAPER AUTHORITY
!=
LIVE AUTHORITY
```

## 8. Owner Governance Flow

للطلبات الـOwner-level التي قد تقود إلى تغيير أو تطوير:

```text
Owner request
→ Web/AI ينظم الطلب ويعرض ما فهمه عند الحاجة
→ الطلب يذهب للـApplication الصحيح
→ Application-owned intelligence يفسر المعنى الدوميني
→ Candidate / isolated work ضمن authority الحقيقية
→ Tests / Validation
→ Results + Evidence
→ Owner decision
→ Next separately authorized stage
```

مثال:

```text
Add Saudi Market
!= Start Testing
!= Paper Trading
!= Tiny Live
!= Live Trading
```

كل مرحلة تحتاج الحالة والـauthority المناسبة لها.

---

## 9. Confirmation for Sensitive Actions

التحليل العادي لا يجب أن يتحول إلى متاهة confirmations.

لكن عندما يقترب الطلب من action حساس أو authority-bearing request، يجب أن توضح الواجهة ما فهمته قبل الإرسال/التأكيد حسب خطورة الطلب والعقد النهائي.

مثال Owner:

```text
I understood your request as:
Authorize Saudi Market Candidate -> Paper Validation

This does NOT authorize Tiny Live or Live Trading.
```

ثم Confirmation واضح عند الحاجة.

وبالنسبة للمستخدم العادي، إذا كانت الجملة يمكن أن تعني مجرد استشارة أو تنفيذًا حقيقيًا، يجب إزالة الغموض قبل أي execution-bearing request.

---

## 10. What Must Remain Distinguishable

الواجهة تميز عند الحاجة بين:

- كلام المستخدم الأصلي.
- AI interpretation / structured intent.
- target Application.
- authoritative source/result.
- freshness/staleness.
- recommendation/advisory result.
- authority decision عندما يوجد.
- execution state عندما يوجد.
- evidence/result identifiers عندما تكون مطلوبة.

رسالة AI تقول `تم` أو `جاهز` ليست بديلًا عن authoritative state/evidence.

---

## 11. Failure and Uncertainty UX

إذا الـAI لم يفهم المقصود بثقة كافية، يسأل المستخدم بطريقة بشرية بدل اختراع intent.

إذا الـApplication أو البيانات غير متاحة، يقول ذلك بوضوح بدل صناعة تحليل وهمي.

إذا البيانات stale أو freshness غير معروفة، يظهر ذلك للمستخدم حسب الـauthoritative metadata المتاحة.

```text
AI DOES NOT KNOW
!=
AI MAY INVENT
```

و:

```text
NO CURRENT DATA
!=
NO RISK
!=
NO CHANGE
```

---

## 12. Generalization to Future Applications

Shared Web يوفر نفس Conversation/Gateway pattern لأي Application مستقبلية.

لكن المعنى يبقى للـApplication المالك:

- Trading meaning يبقى FSATS-owned.
- Accounting meaning يبقى Accounting-owned.
- Warehouse meaning يبقى Warehouse-owned.

المستخدم يتكلم بنفس السهولة عبر Falcon، لكن كل Application يبقى صاحب بياناته ومعناه وقراراته وصلاحياته.

---

## 13. Current Dependency Boundary

FCR-0080 يؤكد أن generic governed communication boundary موجود للتخطيط، بينما exact Application-side producer/consumer/schema/authority/FIL bindings ما زالت Application-owned materialization قبل final UX/runtime freeze.

لذلك يمكن تثبيت تجربة المحادثة كمبدأ UX الآن، لكن لا نخترع exact transport أو runtime route أو command schema.

FCR-0081 يعاد حاليًا مراجعته عند FSATS بسبب Owner clarification بأن user API/broker credentials تخص Automated Trading فقط وليس advisory/non-execution use.

---

هذا الملف لا يعني `APPROVED` ولا يمنح implementation, deployment, Paper, Tiny Live, Live أو execution authority.
