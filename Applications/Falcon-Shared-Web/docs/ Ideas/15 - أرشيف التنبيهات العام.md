# Shared Falcon Web - أرشيف التنبيهات العام

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يسجل اتجاه UX/Product الخاص بأرشيف التنبيهات العام داخل Falcon. لا يمنح implementation/runtime/messaging authority.

---

## 1. نطاق الأرشيف

اعتمد الـOwner أن الأرشيف **لا يقتصر على الحملات والعروض فقط**.

الأرشيف هو مكان رجوع المستخدم إلى **كل أنواع التنبيهات القديمة القابلة للأرشفة** التي انتقلت من قائمة التنبيهات النشطة إلى الأرشيف، ضمن حدود النوع والسياسات الحاكمة لكل تنبيه.

```text
FALCON NOTIFICATION ARCHIVE
=
ALL ARCHIVABLE OLD NOTIFICATION TYPES
```

أمثلة الأنواع قد تشمل بحسب ما هو متاح فعليًا للمستخدم وتبعًا للتطبيق المالك:

- حملات وعروض؛
- إشعارات الاشتراك أو الـVIP؛
- إشعارات Applications المختلفة؛
- التنبيهات المعلوماتية القديمة؛
- أي فئات أخرى قابلة للأرشفة يعرّفها النظام أو الـApplication المالك لاحقًا.

وجود نوع من التنبيه داخل الأرشيف لا ينقل ملكية معناه إلى Shared Web. الـApplication أو الجهة المالكة تبقى صاحبة المعنى والحالة authoritative.

```text
ARCHIVE PRESENTATION != DOMAIN OWNERSHIP
ARCHIVED ITEM != ACTIVE ACTION
HISTORICAL VIEW != CURRENT AUTHORITY
```

### 1.1 الفصل حسب الـApplication

اعتمد الـOwner أن **كل Falcon Application يكون لها Notification Center خاص بها وArchive خاص بها** ضمن تجربة Shared Web، بدل دمج كل تنبيهات Falcon في صندوق واحد مشترك بلا فصل.

```text
APPLICATION A
→ APPLICATION A NOTIFICATION CENTER
→ APPLICATION A ARCHIVE

APPLICATION B
→ APPLICATION B NOTIFICATION CENTER
→ APPLICATION B ARCHIVE
```

هذا الفصل هو فصل عرض وتنظيم وتجربة استخدام، ولا ينقل ملكية معنى التنبيه إلى Shared Web ولا يجعل Shared Web مالكًا لحالة الـApplication.

```text
PER-APPLICATION NOTIFICATION UX
!=
WEB OWNS APPLICATION NOTIFICATION SEMANTICS
```

كل Application يبقى مالكًا لمعنى تنبيهاته وحالتها authoritative، بينما Shared Web يقدم القالب والتجربة المشتركة لعرض مركز التنبيهات والأرشيف الخاص بتلك الـApplication.

الهدف هو أن المستخدم عندما يكون داخل Application معينة يرى تنبيهاتها وسجلها التاريخي بشكل واضح، بدون خلطها افتراضيًا مع تنبيهات Applications أخرى.

### 1.2 عداد غير المقروء في Falcon Home

اعتمد الـOwner أن الـFalcon Home لا يعرض Preview أو نصوص إضافية للتنبيهات. يظهر فقط **رمز الجرس المعتاد للتنبيهات**، ومعه Badge دائرية حمراء صغيرة تحتوي عدد التنبيهات غير المقروءة.

```text
NOTIFICATION BELL
+
RED UNREAD COUNT BADGE
```

الـBadge تعرض الرقم فقط، مثل:

```text
🔔  [4]
```

ولا يظهر معها:

- آخر تنبيه؛
- Preview؛
- Summary؛
- نص إضافي داخل الـFalcon Home.

العدد المعروض يشمل فقط التنبيهات غير المقروءة التابعة للـApplications التي يملك المستخدم اشتراكًا/وصولًا فعليًا إليها.

```text
FALCON HOME UNREAD BADGE COUNT
=
UNREAD NOTIFICATIONS FROM CURRENTLY AUTHORIZED / SUBSCRIBED APPLICATIONS ONLY
```

أي Application غير مشترك بها المستخدم أو لا يملك وصولًا حاليًا إليها لا تدخل تنبيهاتها في هذا العدد ولا تظهر له بسبب وجودها داخل Falcon.

مثال:

```text
USER SUBSCRIPTIONS:
- TRADING
- ACCOUNTING

UNREAD:
- TRADING = 4
- ACCOUNTING = 2

FALCON HOME BELL BADGE = 6
```

ومستخدم مشترك فقط في Trading وله 4 تنبيهات غير مقروءة يرى:

```text
FALCON HOME BELL BADGE = 4
```

هذا العداد هو مؤشر UX مختصر فقط. فتح الجرس يقود المستخدم إلى تجربة التنبيهات، مع بقاء الفصل حسب الـApplication وعدم تحويل Shared Web إلى مالك لمعنى التنبيهات أو الـentitlements.

```text
BELL BADGE = UNREAD COUNT INDICATOR ONLY
BELL BADGE != NOTIFICATION PREVIEW
BELL BADGE != MERGED DOMAIN OWNERSHIP
WEB PRESENTS AUTHORIZED APPLICATION SET
!=
WEB MINTS APPLICATION ENTITLEMENT
```

### 1.3 فتح الجرس وعرض التنبيه بدون مغادرة الصفحة

اعتمد الـOwner أن الضغط على جرس التنبيهات في Falcon Home يفتح **قائمة بسيطة وخفيفة** تحتوي أسماء/عناوين التنبيهات المتاحة للمستخدم، بدون تحويل المستخدم مباشرة إلى صفحة تنبيهات كاملة.

القائمة نفسها موجهة لإنسان، لذلك تكون الأسماء والصياغات مفهومة ومباشرة، وليس على شكل identifiers أو codes أو عبارات داخلية خاصة بالنظام.

عندما يضغط المستخدم على أحد التنبيهات، يفتح التنبيه داخل **Popup / Dialog** فوق الصفحة الحالية.

```text
BELL CLICK
→ SIMPLE NOTIFICATION LIST
→ USER SELECTS ONE NOTIFICATION
→ POPUP / DIALOG OPENS OVER CURRENT PAGE
```

لا يحتاج المستخدم إلى مغادرة الصفحة الحالية فقط من أجل قراءة التنبيه.

يمكن للمستخدم إغلاق مربع الحوار بشكل طبيعي عن طريق زر `×`.

```text
OPEN NOTIFICATION != NAVIGATE TO FULL NOTIFICATION PAGE
CLOSE × = DISMISS DIALOG VIEW
```

إغلاق الـPopup بالـ`×` هو إغلاق لواجهة العرض فقط، ولا يُفترض منه وحده تغيير أي حالة business/domain أو حذف السجل أو تغيير الحقيقة authoritative الخاصة بالتنبيه.

### 1.4 قاعدة اللغة البشرية في واجهة المستخدم

اعتمد الـOwner قاعدة عامة لهذه التجربة: **كل نص ظاهر للمستخدم يجب أن يُكتب بصيغة بشرية طبيعية ومفهومة، لأن المتلقي مستخدم بشري وليس نظامًا آليًا.**

هذا يشمل، بحسب السياق:

- أسماء التنبيهات؛
- عناوين الـPopup/Dialog؛
- الرسائل والـSummaries؛
- حالات النجاح أو الفشل؛
- الشروحات القصيرة؛
- الأزرار والتوجيهات المرئية للمستخدم.

مثال مقبول للمستخدم:

```text
مشكلة في الاتصال، تم حلها.
```

بدل عرض صيغة داخلية مثل:

```text
CONNECTION_FAILURE_RESOLVED / EVENT_0042
```

يمكن الاحتفاظ بالـIDs أو codes أو المصطلحات التقنية داخليًا إذا احتاجتها العقود أو التشغيل أو الأدلة، لكن **لا تُستخدم كلغة المستخدم الافتراضية**.

```text
USER-FACING LANGUAGE = HUMAN / CLEAR / NATURAL
INTERNAL MACHINE IDENTIFIERS != DEFAULT USER COPY
```

هذه القاعدة تخص أسلوب العرض ولا تمنح Shared Web حق تغيير المعنى authoritative القادم من الجهة المالكة. يجوز تبسيط الصياغة للمستخدم بشرط عدم اختراع سبب أو نتيجة أو حالة غير موجودة في المصدر الموثوق.

## 2. تجربة الاستخدام البديهية

بناءً على توجيه الـOwner بأن التفاصيل الـUX البديهية تُختار بما يحقق راحة المستخدم، يعتمد الأرشيف العام مبدئيًا وسائل الوصول المعتادة والمفيدة بدون الحاجة إلى قرار Owner منفصل لكل تفصيلة صغيرة، مثل:

- البحث؛
- فلترة الفترة الزمنية عند الحاجة؛
- Clear / Reset للفلاتر؛
- حالات Empty State واضحة؛
- تحميل/تقسيم مناسب عند زيادة عدد العناصر؛
- إبقاء حالة العنصر ونوعه ومصدره واضحة للمستخدم.

هذه التفاصيل تبقى UX convenience فقط ولا تغير معنى التنبيه أو صلاحيته أو authority الخاصة به.

## 3. علاقة هذا القرار بقرارات الحملات السابقة

القرارات التفصيلية الخاصة بالحملات والعروض المسجلة في:

`14 - معاينة الحملة قبل النشر.md`

تبقى سارية على تلك الفئة، ومنها القراءة، النقل إلى الأرشيف، الحذف المؤكد، عرض حالة `Expired`، وعدم إظهار CTA للعرض المنتهي.

هذا الملف يوسع **نطاق الأرشيف** ليكون عامًا لكل أنواع التنبيهات القديمة القابلة للأرشفة، لكنه لا يعمم تلقائيًا كل قواعد الحملات على كل نوع تنبيه إذا كان لذلك النوع معنى أمني أو قانوني أو تشغيلي مختلف.

```text
GENERAL ARCHIVE SCOPE
!=
AUTOMATICALLY IDENTICAL DELETE / RETENTION RULES FOR EVERY NOTIFICATION TYPE
```

## 4. تنبيهات الأمن والطوارئ الحرجة تبقى في مركز التنبيهات

اعتمد الـOwner أن **تنبيهات الأمن والطوارئ الحرجة لا تنتقل إلى الأرشيف طالما أن الحالة الحرجة ما زالت فعالة**.

هذه الفئة تبقى موجودة في **مركز التنبيهات النشط** بدل أن يعاملها المستخدم كتنبيه قديم عادي يمكن نقله إلى الأرشيف.

```text
ACTIVE CRITICAL SECURITY / EMERGENCY NOTIFICATION
→
REMAINS IN ACTIVE NOTIFICATION CENTER

ACTIVE CRITICAL SECURITY / EMERGENCY NOTIFICATION
!=
NORMAL ARCHIVABLE NOTIFICATION
```

هذا القرار يخص موقع ظهور هذه التنبيهات في تجربة المستخدم ولا يحدد من يقرر أن الحدث أصبح `Critical` أو `Security` أو `Emergency`. تصنيف معنى الحدث وشدته يبقى من مسؤولية الجهة authoritative المالكة وفق العقود والسياسات الحاكمة، بينما Shared Web يعرض التصنيف الناتج ولا يخترعه.

```text
WEB PRESENTS CRITICAL CLASSIFICATION
!=
WEB DEFINES SECURITY / EMERGENCY SEVERITY
```

كما أن بقاء التنبيه في مركز التنبيهات لا يعني أن Shared Web يملك سلطة احتوائه أو إغلاق الحادثة أو تغيير حالتها التشغيلية.

```text
VISIBLE IN ACTIVE NOTIFICATIONS
!=
INCIDENT RESOLVED
!=
SECURITY CONDITION CLEARED
```

### 4.1 الانتقال التلقائي إلى الأرشيف بعد انتهاء الحالة الحرجة

اعتمد الـOwner أنه عندما تعتبر الجهة authoritative المالكة أن حالة الأمن/الطوارئ الحرجة **انتهت رسميًا**، ينتقل التنبيه تلقائيًا من مركز التنبيهات النشط إلى الأرشيف.

لا يحتاج المستخدم إلى إزالة التنبيه يدويًا بعد انتهاء الحالة المعتمدة.

```text
ACTIVE CRITICAL ALERT
→
AUTHORITATIVE SOURCE CONFIRMS CONDITION ENDED / CLEARED
→
AUTOMATIC MOVE TO ARCHIVE
```

وتبقى الحدود التالية إلزامية:

```text
WEB DOES NOT DECLARE INCIDENT RESOLVED
WEB DOES NOT CLEAR SECURITY CONDITION
AUTOMATIC ARCHIVE TRANSITION REQUIRES AUTHORITATIVE RESOLUTION STATE
ARCHIVED CRITICAL ALERT = HISTORICAL / RESOLVED PRESENTATION
ARCHIVED != ERASED AUDIT / SECURITY EVIDENCE
```

إذا كانت حالة الانتهاء `UNKNOWN` أو `STALE` أو `UNAVAILABLE`، لا يفترض الـWeb أن الحالة انتهت ولا ينقل التنبيه تلقائيًا للأرشيف على هذا الأساس.

```text
UNKNOWN / STALE / UNAVAILABLE RESOLUTION STATE
!=
SAFE TO AUTO-ARCHIVE
```

### 4.2 التنبيهات الحرجة المؤرشفة تبقى دائمًا وغير قابلة للحذف

اعتمد الـOwner أن تنبيهات الأمن والطوارئ الحرجة، بعد انتقالها تلقائيًا إلى الأرشيف بسبب انتهاء الحالة رسميًا، **تبقى محفوظة في أرشيف المستخدم بشكل دائم من منظور تجربة المستخدم ولا تكون قابلة للحذف منه**.

لا يظهر لهذه الفئة خيار `Delete` في الأرشيف، ولا تنطبق عليها قاعدة الحذف النهائي المتاحة لبعض أنواع التنبيهات العادية أو الحملات.

```text
RESOLVED CRITICAL SECURITY / EMERGENCY ALERT
→
AUTOMATIC ARCHIVE
→
PERMANENT USER-VISIBLE ARCHIVE HISTORY
→
NO USER DELETE
```

وتبقى الفروقات التالية إلزامية:

```text
CRITICAL ALERT ARCHIVE != NORMAL DELETABLE ARCHIVE ITEM
NO USER DELETE != ACTIVE INCIDENT
ARCHIVED PERMANENTLY != INCIDENT STILL OPEN
PERMANENT USER-VISIBLE HISTORY != WEB OWNS SECURITY RECORD AUTHORITY
```

هذا القرار يثبت سلوك الـUX لهذه الفئة ولا يحدد وحده شكل التخزين التقني أو سجل التدقيق الأمني الخلفي. أي متطلبات أوسع للاحتفاظ الأمني أو القانوني تبقى خاضعة للجهة المالكة والعقود والسياسات الحاكمة.

### 4.3 الحالة المرئية للتنبيه الأمني/الطارئ المؤرشف

اعتمد الـOwner أن أي تنبيه أمني أو طارئ حرج انتقل إلى الأرشيف بعد تأكيد انتهاء الحالة رسميًا يجب أن يظهر للمستخدم بوضوح بحالة **`Resolved`**.

الهدف هو منع أي التباس بين سجل تاريخي لحادثة انتهت وبين خطر ما زال قائمًا.

```text
ARCHIVED CRITICAL SECURITY / EMERGENCY ALERT
→
VISIBLE STATUS = RESOLVED
```

وتبقى الحدود التالية إلزامية:

```text
RESOLVED LABEL != WEB RESOLUTION AUTHORITY
RESOLVED LABEL REQUIRES AUTHORITATIVE RESOLUTION STATE
RESOLVED != DELETED
RESOLVED != HIDDEN
RESOLVED != FORGETTABLE
```

الـShared Web يعرض حالة `Resolved` الناتجة عن الجهة authoritative ولا يقررها من تلقاء نفسه.

### 4.4 عرض التنبيه الأمني/الطارئ المحلول في الأرشيف

اعتمد الـOwner أن التنبيه الأمني أو الطارئ الحرج بعد انتقاله إلى الأرشيف بحالة `Resolved` يظهر للمستخدم على شكل **Summary مختصر**، وليس كتفاصيل حادثة كاملة داخل الأرشيف العام.

```text
RESOLVED CRITICAL SECURITY / EMERGENCY ALERT
→
ARCHIVE PRESENTATION = SUMMARY
```

الغرض من الأرشيف هنا هو إبقاء سجل واضح ومفهوم للمستخدم بدون تحويل الأرشيف العام إلى شاشة تحقيق أمني أو سجل تشغيلي تفصيلي.

الـSummary يكون **جملة بشرية بسيطة ومباشرة** توضح باختصار ما المشكلة التي حدثت وما نتيجتها النهائية، بدون تفاصيل تقنية غير لازمة للمستخدم.

مثال توضيحي:

```text
مشكلة في الاتصال، تم حلها.
Status: Resolved
```

وبنفس النمط يمكن أن تكون الرسالة مثل:

```text
انقطاع مؤقت في الخدمة، تم استعادتها.
Status: Resolved
```

المقصود هو أن المستخدم يفهم فورًا: **ماذا حدث؟ وهل انتهت المشكلة؟** بدون الحاجة لفتح سجل حادثة كامل.

```text
USER SUMMARY = SIMPLE PROBLEM + FINAL OUTCOME
SUMMARY != ROOT-CAUSE ANALYSIS
SUMMARY != FULL TECHNICAL TIMELINE
SUMMARY != SECURITY INVESTIGATION RECORD
```

يجب أن يبقى الـSummary صادقًا مع الحالة authoritative، ويُظهر على الأقل ما يلزم لفهم أن هناك حادثة سابقة انتهت، مع إبراز `Resolved` بوضوح. أما التفاصيل التقنية أو الأمنية الحساسة أو الأدلة الكاملة فلا تُفترض جزءًا من هذا العرض العام لمجرد وجود التنبيه في الأرشيف.

```text
SUMMARY VIEW != FULL INCIDENT RECORD
SUMMARY VIEW != SECURITY INVESTIGATION SURFACE
SUMMARY VIEW != AUDIT / EVIDENCE STORE
WEB SUMMARY != AUTHORITY TO REDACT OR REDEFINE SOURCE TRUTH
```

الصياغة الدقيقة للـSummary يمكن تحسينها UX-wise لاحقًا بما يجعلها مفهومة وطبيعية للمستخدم، لكن بدون اختراع سبب أو نتيجة غير موجودة في الحالة authoritative الأصلية.

## 5. Boundaries

هذا القرار لا يحدد:

- exact storage implementation؛
- retention القانونية أو الأمنية خارج قرار بقاء هذه التنبيهات الحرجة في الأرشيف المرئي للمستخدم؛
- backend audit/evidence retention؛
- delivery routes أو provider implementation؛
- authority التي تصنف التنبيه كأمني/طارئ/حرج أو تثبت انتهاء الحالة.

هذه النقاط تُحسم حسب الجهة المالكة والعقود والسياسات الحاكمة عندما نصل إلى التصميم التفصيلي المناسب.

```text
USER ARCHIVE UX != AUDIT RECORD
USER DELETE != AUTOMATIC LEGAL / SECURITY EVIDENCE DELETE
ARCHIVE SCOPE != DELIVERY AUTHORITY
CRITICAL NOTIFICATION VISIBILITY != INCIDENT AUTHORITY
```
