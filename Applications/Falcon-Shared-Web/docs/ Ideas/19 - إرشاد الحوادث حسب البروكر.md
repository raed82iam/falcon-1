# Shared Falcon Web - إرشاد الحوادث حسب البروكر

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يثبت قرار الـProject Owner بأن Smart Web لا يجوز أن يخترع خطوات إرشاد المستخدم أثناء حادث broker/API من ذاكرته أو من تعليمات عامة غير مرتبطة بالبروكر الفعلي.

لا يمنح هذا الملف implementation/runtime/trading/authorization authority.

---

## 1. القاعدة الأساسية

عند وقوع incident مرتبط ببروكر مستخدم معيّن:

```text
IDENTIFY EXACT BROKER / ACCOUNT CONTEXT
-> OBTAIN APPLICATION BUSINESS FACT/ACTION NEED
-> RESEARCH CURRENT BROKER-SPECIFIC USER PATH
-> VERIFY GUIDANCE AGAINST TRUSTED CURRENT SOURCES
-> TRANSLATE INTO CALM HUMAN STEP-BY-STEP UX
-> COLLECT USER RESULT / EVIDENCE
-> RETURN ONLY REQUIRED RESULT / EVIDENCE TO APPLICATION
```

Shared Web SHALL NOT:

- يخترع أسماء صفحات أو أزرار في واجهة البروكر.
- يعتمد على ذاكرة قديمة عن واجهة البروكر إذا كان يمكن التحقق من المصدر الحالي.
- يعطي المستخدم مسارًا خاصًا ببروكر مختلف.
- يطلب من المستخدم تنفيذ order/action غير مطلوب من Application semantics.
- يحوّل تعليمات عامة إلى trading authority.

---

## 2. Broker Guidance Resolver

يخطط Shared Web لطبقة UX/knowledge behavior باسم وصفي مؤقت:

`Broker Guidance Resolver`

وظيفتها ليست اتخاذ قرار التداول، بل تحويل طلب Application إلى مسار إرشاد صحيح للمستخدم داخل البروكر الفعلي.

مدخلاتها تشمل، عندما تكون متاحة ومخولة:

- broker identity.
- environment مثل Paper/Live عندما يغيّر مسار الواجهة.
- نوع المشكلة التي حددها Application.
- المعلومة أو الإجراء المطلوب من المستخدم.
- اللغة/locale المناسبة للمستخدم.
- device/context إن كان له أثر حقيقي على واجهة البروكر.

مخرجاتها:

- خطوات بشرية قصيرة ومتحققة.
- أسماء الصفحات/الأقسام كما تظهر للمستخدم قدر الإمكان.
- ما الذي يجب أن يبحث عنه المستخدم على الشاشة.
- أي تحذير ضروري قبل الخطوة.
- نوع evidence المطلوب إرجاعه: إجابة، screenshot، confirmation، أو غيره ضمن الحدود المسموحة.

---

## 3. Fresh broker research rule

عندما يكون الإرشاد حساسًا أو قد تتغير واجهة البروكر، Shared Web لا يعتمد على تعليمات قديمة فقط.

الأولوية في البحث تكون للمصادر الرسمية الحالية الخاصة بالبروكر، مثل:

1. official broker help/support center.
2. official broker documentation.
3. official broker status/service information عندما المشكلة قد تكون outage.
4. official broker UI guides / screenshots / account help where available.

المصادر غير الرسمية لا تصبح المرجع الأساسي لمسار حساس إذا توفر مصدر رسمي.

إذا تعذر إثبات مكان الزر/الصفحة الحالية:

```text
UNKNOWN UI PATH != SAFE TO INVENT
```

ويجب أن يتحول الإرشاد إلى صيغة محافظة، مثل وصف المعلومة المطلوب الوصول إليها بدل اختراع navigation path غير مؤكد.

---

## 4. الفصل بين Application وWeb

Application/FSATS يحدد:

- ما المشكلة التجارية/التنفيذية.
- ما الذي يعرفه وما الذي لا يعرفه.
- ما المعلومة المطلوبة من المستخدم الآن.
- ما الإجراء التجاري المطلوب أو المسموح semanticًا.
- متى يحتاج دليلًا أحدث.
- كيف تؤثر النتيجة على reconciliation/recovery.

Shared Web يحدد:

- كيف نشرح المشكلة للمستخدم.
- كيف نهديه داخل واجهة البروكر الفعلي.
- أي source/current UI path نستخدم للإرشاد.
- كيف نعرض الخطوات بدون إرباك.
- كيف نطلب screenshot أو confirmation.
- كيف نجمع الرد ونرجعه للـApplication.

```text
APPLICATION DEFINES WHAT IS NEEDED
WEB DETERMINES HOW TO HELP THE HUMAN FIND/PROVIDE IT
```

---

## 5. Calm guidance rule

الهدف ليس فقط أن تكون الخطوات صحيحة، بل أن تكون نفسيًا مناسبة وقت الأزمة.

Shared Web SHALL:

- يبدأ بجملة قصيرة تخبر المستخدم ما الذي يحدث بدون تهويل.
- يوضح ما الذي فعله Falcon لحمايته إن كان ذلك authoritative، مثل إيقاف فتح مخاطر جديدة.
- يعطي **خطوة واحدة واضحة في كل مرة**.
- لا يعرض قائمة طويلة من الاحتمالات دفعة واحدة.
- لا يستخدم لغة كارثية إذا لم تكن semantics تستدعيها.
- لا يخفي uncertainty.
- لا يحمل المستخدم مصطلحات داخلية أو أكواد تقنية.
- بعد كل خطوة يوضح ببساطة ما الذي يحتاجه الآن.

مثال UX عام:

```text
في مشكلة بالاتصال بحساب التداول، وFalcon أوقف فتح مخاطر جديدة على هذا الحساب مؤقتًا.

خلينا نتحقق من الحالة خطوة بخطوة.

افتح تطبيق/موقع البروكر. سأدلك على المكان المطلوب حسب واجهة البروكر المستخدمة عندك.
```

ثم يعرض خطوة broker-specific واحدة بعد التحقق من المسار.

---

## 6. Page-aware guidance

إذا أمكن معرفة الصفحة الحالية أو استلام screenshot من المستخدم، Web يستخدم هذا السياق لتقليل الخطوات.

مثال:

بدل:
`اذهب إلى الحساب ثم التداول ثم المراكز ثم...`

إذا الصورة تثبت أن المستخدم موجود أصلًا في Open Positions:

`ممتاز، أنت في المكان الصحيح. شوف مركز XYZ وقل لي الكمية الظاهرة.`

لكن:

```text
PAGE CONTEXT != BROKER TRUTH
SCREENSHOT OBSERVATION != BROKER API CONFIRMATION
```

## 7. No-panic interaction pattern

عند incident حساس، العرض المقترح:

1. **ما الذي حدث؟** سطر واحد.
2. **ما الذي فعله Falcon الآن؟** فقط إذا authoritative.
3. **ما الذي نحتاج نتأكد منه؟** شيء واحد.
4. **أين تجده في البروكر؟** broker-specific verified guidance.
5. **ماذا ترسل لنا؟** إجابة/صورة محددة.
6. **ثم الخطوة التالية فقط.**

لا نعرض للمستخدم كل سيناريوهات الخطر والتحليل الداخلي في أول شاشة.

التفاصيل الإضافية تظهر progressive disclosure عندما يحتاجها.

---

## 8. Broker UI change handling

واجهات البروكر قد تتغير.

لذلك أي broker-specific runbook أو cached guidance يجب أن يحمل ما يكفي لمعرفة:

- broker/product identity.
- environment applicability.
- source/reference.
- last verified/reviewed time where applicable.

وقبل الاعتماد على guidance حساس قديم، يجب إعادة التحقق عندما توجد دلالة معقولة أن الواجهة/السياسة تغيرت.

```text
KNOWN OLD BROKER PATH != CURRENT VERIFIED BROKER PATH
```

---

## 9. Outage distinction

قبل أن نطلب من المستخدم إصلاح credentials أو تغيير إعدادات، يجب عدم افتراض أن الخلل من حسابه فقط إذا قد يكون البروكر نفسه متعطلًا.

إذا كان incident semantic يسمح بذلك، Web يمكنه التحقق من official broker service/status information كجزء من الإرشاد.

لكن Web لا يعيد تصنيف trading incident من نفسه. يعرض المعلومة الموثوقة ويرجع evidence/observation المطلوب للـApplication.

---

## 10. Safety and privacy

أثناء broker-specific guidance:

- لا نطلب password.
- لا نطلب OTP/MFA code.
- لا نطلب API secret داخل chat/notification.
- لا نطلب معلومات ليست لازمة للمشكلة.
- إذا screenshot يحتوي معلومات حساسة غير لازمة، نوجه المستخدم لإخفائها عندما يكون ذلك عمليًا.
- secure credential update يبقى في governed credential path وليس ordinary incident chat.

---

## 11. Current planning effect on FCR-0095

هذه القاعدة توسع Web-owned incident UX planning ولا تغير Application-owned trading semantics.

FCR-0095 يبقى:

```text
OPEN
Waiting On: WEB
WEB IMPLEMENTATION = PENDING
GOVERNED VERIFICATION = PENDING
```

ولا يصبح مؤهلًا للإغلاق إلا بعد التنفيذ الفعلي والتحقق المطلوب.
