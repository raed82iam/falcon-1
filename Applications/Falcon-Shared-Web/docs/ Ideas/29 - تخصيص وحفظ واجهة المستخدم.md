# Shared Falcon Web - تخصيص وحفظ واجهة المستخدم

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يسجل قرار الـOwner الخاص بتخصيص المستخدم لواجهة FSATS التي تم قبول اتجاهها البصري في النقاش الحالي. هذا قرار Shared Web presentation/UX فقط، ولا يمنح implementation/runtime/trading authority ولا يغير أي business truth أو Application-owned semantics.

---

## 1. اتجاه واجهة المستخدم

قرار الـOwner:

اتجاه واجهة المستخدم المرئي الذي تم عرضه للمحفظة/الأداء/المراكز/النشاط مقبول كاتجاه UX، مع إضافة أن الواجهة لا تكون ثابتة rigid grid، بل تصبح Workspace قابلًا للتخصيص من المستخدم.

```text
USER DASHBOARD = CUSTOMIZABLE WORKSPACE
DEFAULT LAYOUT != FORCED PERMANENT LAYOUT
```

---

## 2. تغيير حجم المربعات / Widgets

المربعات مثل:

- Portfolio Performance chart.
- Allocation.
- Open Positions.
- Recent Trades.
- Alerts.
- Financial summary cards أو المجموعات التي يسمح التصميم بتحريكها.

تكون قابلة لتغيير الحجم ضمن حدود responsive ومعقولة يمنع معها كسر المحتوى.

المستخدم يستطيع مثلًا:

- تكبير الشارت ليأخذ مساحة أكبر.
- تصغير صندوق آخر أقل أهمية له.
- توسيع جدول المراكز ليعرض معلومات أكثر.

```text
USER MAY RESIZE ELIGIBLE WIDGETS
RESIZE MUST PRESERVE READABILITY
RESIZE MUST NOT ALTER BUSINESS MEANING
```

---

## 3. إعادة ترتيب المربعات

المستخدم يستطيع سحب المربعات المؤهلة وإعادة ترتيبها داخل الـWorkspace.

الواجهة تستخدم grid/snap behavior مريح بدل الحركة الحرة غير المنضبطة، حتى لا تتحول الصفحة إلى فوضى بصرية.

```text
USER MAY REORDER ELIGIBLE WIDGETS
LAYOUT ENGINE MAY SNAP/REFLOW FOR USABILITY
```

---

## 4. إخفاء مربع مؤقتًا

كل widget قابل للإخفاء يملك خيارًا واضحًا مثل `Hide` أو `Remove from dashboard`.

إخفاء المربع:

- لا يحذف بيانات المستخدم.
- لا يلغي capability.
- لا يغير أي entitlement.
- لا يغير Application state.

هو فقط presentation preference.

```text
HIDE WIDGET != DELETE DATA
HIDE WIDGET != DISABLE CAPABILITY
HIDE WIDGET != CHANGE ENTITLEMENT
```

---

## 5. إدارة واسترجاع المربعات المخفية

يوجد خيار دائم وواضح مثل:

`Customize Dashboard`
أو
`Manage Widgets`

ومن خلاله يرى المستخدم قائمة المربعات المتاحة له ويستطيع إعادة أي مربع أخفاه سابقًا.

يجب أيضًا توفير خيار:

`Reset to Default Layout`

كإجراء reversible وآمن يعيد ترتيب Falcon الافتراضي بدون المساس ببيانات الحساب أو إعدادات التداول.

---

## 6. الحفظ والاسترجاع بين الجلسات

أي تغيير layout مؤكد من المستخدم يتم حفظه ضمن Web-owned user presentation preferences:

- ترتيب الـwidgets.
- أبعاد كل widget ضمن النموذج المدعوم.
- visible/hidden state.
- أي presentation-only state يسمح التصميم بحفظه مستقبلًا.

وعند تسجيل الخروج أو إغلاق المتصفح ثم العودة لاحقًا، تعاد نفس الواجهة المحفوظة للمستخدم.

```text
USER SAVED LAYOUT
-> PERSISTS ACROSS LOGOUT / LOGIN
-> PERSISTS ACROSS BROWSER RESTART
-> RESTORES LAST SAVED SUPPORTED LAYOUT
```

الحفظ يجب أن يكون مرتبطًا بحساب Falcon للمستخدم، لا بجهاز واحد فقط، حتى ترجع تفضيلاته عند استخدام جهاز آخر حيثما تسمح بنية Web بذلك.

---

## 7. Auto-save UX

الاتجاه المفضل للراحة:

- resize/reorder/hide يعطى feedback فوري.
- التغيير يُحفظ تلقائيًا بعد استقرار الحركة بدل إجبار المستخدم على الضغط على Save بعد كل تعديل.
- يظهر feedback خفيف مثل `Layout saved` عند الحاجة، بدون إزعاج.

إذا فشل حفظ التفضيل، لا ندعي أن الحفظ نجح، وتظل الواجهة الحالية usable مع تنبيه presentation-level مناسب.

```text
LOCAL VISUAL CHANGE != SERVER-SAVED PREFERENCE
SAVE FAILED != SAVED
```

---

## 8. Responsive layouts

Desktop وTablet وMobile Web لا يجب أن يتشاركوا إحداثيات pixel واحدة حرفيًا.

الـShared Web يبقى responsive بما يكفي للتوافق والوصول عند الحاجة، لكن Mobile Web ليس المنتج الأساسي للموبايل.

مثال:

```text
DESKTOP -> MULTI-COLUMN RESIZABLE GRID
TABLET  -> REDUCED-COLUMN ADAPTIVE GRID
MOBILE WEB -> COMPATIBILITY / FALLBACK ONLY
```

إذا فتح المستخدم الويب من الهاتف، يعاد reflow للمحتوى بدل عرض نسخة مكسورة من حجم desktop، بدون اعتبار ذلك بديلًا عن تطبيق الموبايل المخصص.

---

## 9. حدود التخصيص

ليس كل شيء قابلًا للإخفاء أو التصغير بلا حدود.

Shared Web يستطيع وضع minimum/maximum sizes وقواعد pinned presentation لعناصر سلامة/تنبيه حرجة عندما تفرض العقود أو قواعد Falcon ذلك.

كذلك لا يسمح التخصيص للمستخدم بأن:

- يغير business truth.
- يخفي حقيقة حرجة عندما يلزم قانونيًا/أمنيًا عرضها.
- يحول stale إلى current.
- يغير status أو order/trade state.
- يكتسب capability غير مشمولة بخطته.

```text
CUSTOMIZATION = PRESENTATION PREFERENCE
CUSTOMIZATION != BUSINESS AUTHORITY
CUSTOMIZATION != ENTITLEMENT AUTHORITY
CUSTOMIZATION != TRUTH OVERRIDE
```

---

## 10. العلاقة مع بيانات FCR-0133

Widgets المحفظة والمراكز والنشاط والأداء تعرض فقط الـApplication-owned projections المعرفة عبر FCR-0133.

تغيير مكان أو حجم أو visibility الـwidget لا يغير البيانات نفسها ولا طريقة احتسابها.

```text
WIDGET LAYOUT != PORTFOLIO TRUTH
WIDGET VISIBILITY != DATA AVAILABILITY
WIDGET SIZE != METRIC SEMANTICS
```

---

## 11. نطاق تطبيق الموبايل المستقبلي

قرار الـOwner:

تطبيق الموبايل المستقبلي **ليس تطبيق Falcon عامًا لكل Applications**.

هو تطبيق موبايل مخصص فقط لـTrading Application / FSATS وتجربة التداول المرتبطة بها.

```text
MOBILE APPLICATION SCOPE = TRADING APPLICATION / FSATS ONLY
MOBILE APPLICATION SCOPE != ALL FALCON APPLICATIONS
MOBILE APPLICATION != GENERAL FALCON HOST SHELL
```

بالتالي:

- لا نخطط له كواجهة موحدة لباقي Falcon Applications.
- لا نضيف تنقلًا عامًا بين Applications الأخرى لمجرد أنها موجودة داخل Falcon.
- أي capabilities تظهر في تطبيق الموبايل يجب أن تكون مرتبطة بتجربة FSATS/Trading أو بما يخدمها صراحةً ضمن العقود المعتمدة.
- Shared Web يبقى surface منفصلًا، وتطبيق الموبايل المستقبلي surface مستقل موجه للتداول فقط.

هذا القرار لا يمنح authority لبناء تطبيق الموبايل الآن ولا يحدد معماريته التقنية أو عقوده التنفيذية. تصميمه وتنفيذه لهما مرحلة مستقلة لاحقًا.
