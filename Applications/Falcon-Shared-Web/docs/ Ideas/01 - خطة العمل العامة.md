# Shared Falcon Web - خطة العمل العامة

**Status:** `DRAFT WORK PLAN / DISCUSSION ONLY`

هذه الخطة ليست موافقة على البرمجة أو التشغيل. هدفها أن نعرف ماذا سنفعل، بأي ترتيب، ومتى نعتبر كل خطوة واضحة بما يكفي للانتقال لما بعدها.

## المرحلة 1 - نفهم ماذا يجب أن يفعل الموقع

نجمع وظائف Shared Falcon Web كلها في صورة واحدة واضحة:
- ماذا يرى الـOwner عند فتح Falcon.
- ماذا يرى المستخدم العادي.
- ما المعلومات التي تأتي من Foundation.
- ما المعلومات التي تأتي من كل Application.
- ما الأشياء للعرض فقط.
- ما الأشياء التي قد تصبح أوامر لاحقًا بعد وجود authority حقيقية.
- ما الذي يجب أن يبقى خارج الويب أصلًا.

النتيجة المطلوبة: قائمة وظائف واضحة بدون افتراض capabilities غير موجودة.

## المرحلة 2 - نرسم خريطة الموقع

نحدد الصفحات الرئيسية ومهمة كل صفحة، ثم مسار التنقل بينها.

## المرحلة 3 - نحدد لغة الحالات

يجب أن يفهم المستخدم الفرق بين حالات مثل:
`HEALTHY`, `DEGRADED`, `UNKNOWN`, `ACTIVE DESIGN`, `NOT AUTHORIZED`, `AWAITING OWNER`, `CONTAINED`.

ويجب ألا نخلط بين:
`PASS`, `OWNER ACCEPTED`, `AUTHORIZED`, `RUNNING`.

## المرحلة 4 - نصمم بوابة الحوار بين الـOwner والـApplications

الـOwner يتكلم بلغة طبيعية، والـWeb يرتب الطلب ويوصله، لكن الـApplication هو صاحب المعنى الدوميني وصاحب النتيجة الحقيقية.

## المرحلة 5 - نصمم المستخدمين والـSuper User

نحدد UX لإدارة المستخدمين، الوصول، وما يظهر للـOwner فقط، مع ترك Authentication وAuthorization الفعليين للـFoundation contracts لاحقًا.

## المرحلة 6 - نصمم Falcon Control

كل زر تحكم يجب أن يطلب من المالك الحقيقي تنفيذ الإجراء ويعرض النتيجة authoritative. ضغط الزر وحده لا يعني نجاحًا.

## المرحلة 7 - نصمم Emergency AI Control

نصمم تجربة الطوارئ والـKill من منظور المستخدم، بدون ادعاء أن الـWeb هو Kill Authority.

## المرحلة 8 - نصمم تطبيق Falcon Emergency Control للموبايل

تطبيق بسيط للطوارئ، مستقل عن الويب قدر الإمكان، يعرض أقل حالة لازمة ويتيح طلب Kill عندما تصبح البنية الحقيقية موجودة.

## المرحلة 9 - نحدد طريقة استضافة Applications داخل الواجهة

الـWeb يبقى Shared shell. كل Application يملك معناه وبياناته وأوامره الخاصة.

## المرحلة 10 - نصمم Audit / Activity

يجب أن يستطيع الـOwner الرجوع لاحقًا ومعرفة: ماذا طلب، ماذا فهم النظام، من سمح، ماذا حصل، وما الدليل.

## المرحلة 11 - نرسم Wireframes

نختبر أماكن الوظائف والتنقل قبل الاهتمام بالشكل النهائي.

## المرحلة 12 - نعمل Visual Design وMockups

بعد ثبات الوظائف، نطور الشكل البصري الحقيقي للويب والموبايل.

## المرحلة 13 - Architecture / Consistency / Security / Red Team

نراجع الخطة ضد Falcon Vision وConstitution وAPP-001 وCON-023 وADR-I012 وADR-I015 وحدود Foundation/Application.

## المرحلة 14 - Owner Review

نعرض النسخة المتكاملة على الـProject Owner. أي تعديل جوهري يرجع للدورة المناسبة قبل القبول النهائي.

## المرحلة 15 - Implementation Planning لاحقًا فقط

بعد الموافقة والـauthority المناسبة فقط يتم تقسيم التنفيذ إلى Work Packages وتحديد التقنية والاختبارات والتكامل والنشر.

## قاعدة الاستمرار

إذا ظهرت معلومة ناقصة من Foundation أو Application:

`نسجل Dependency -> نفتح/نحدث FCR عند الحاجة -> نكمل باقي الأشياء غير المتوقفة عليها`

وجود dependency واحدة لا يوقف تخطيط الويب كله.

## قاعدة قرارات UX البديهية

اعتمد الـOwner أن التفاصيل البديهية منخفضة المخاطر في تجربة المستخدم لا تحتاج إلى إيقاف الحوار وطلب قرار مستقل في كل مرة. عندما تكون المسألة مجرد اختيار UX معتاد لا يغيّر المعنى التجاري، ولا الصلاحيات، ولا حدود Application/Foundation، ولا سياسة قانونية/خصوصية، ولا سلوك أمني أو مالي أو تنفيذي، يختار Shared Web أثناء التخطيط الخيار الأفضل والأبسط لراحة المستخدم وفق ممارسات UX السليمة.

أمثلة ذلك تشمل عند الحاجة:
- Search وFilters وDate Range عندما تكون مفيدة طبيعيًا لقائمة كبيرة؛
- Clear/Reset للبحث والفلاتر؛
- Empty states ورسائل no-results؛
- pagination أو lazy loading بحسب الأنسب؛
- ترتيب وعرض عناصر التحكم المألوفة؛
- حفظ حالة واجهة غير حساسة عندما يحسن تجربة المستخدم ولا يخلق معنى تجاريًا جديدًا.

```text
OBVIOUS LOW-RISK UX DETAIL
→
CHOOSE BEST USER-COMFORT OPTION
→
DO NOT INTERRUPT OWNER FOR MICRO-DECISION
```

لكن هذه القاعدة لا تفوّض Shared Web لاتخاذ قرار نيابة عن الـOwner إذا كان القرار يغيّر:

```text
BUSINESS SEMANTICS
AUTHORITY / PERMISSIONS
ENTITLEMENT / SUBSCRIPTION RULES
SECURITY / PRIVACY / LEGAL POLICY
FINANCIAL OR TRADING BEHAVIOR
DATA RETENTION / DELETION MEANING
CROSS-WORKSTREAM OWNERSHIP
EMERGENCY / KILL SEMANTICS
```

في هذه الحالات يبقى قرار الـOwner أو FCR المناسب مطلوبًا حسب قواعد الـworkstream.

هذه الخطة لا تمنح `IMPLEMENTATION AUTHORITY`, `RUNTIME AUTHORITY`, `DEPLOYMENT AUTHORITY`, `PAPER`, `TINY LIVE`, أو `LIVE` authority.
