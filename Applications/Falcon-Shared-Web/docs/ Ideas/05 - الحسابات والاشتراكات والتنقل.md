# Shared Falcon Web - الحسابات والاشتراكات والتنقل

**Status:** `DRAFT / DISCUSSION ONLY`

هذا الملف يسجل الاتجاه الحالي لتجربة الحسابات والاشتراكات والتنقل بين Falcon Applications.

هو تخطيط UX/Product فقط. لا يحدد أو يمنح Authentication/Session/Identity/Runtime authority ولا يختار آلية تقنية نهائية.

---

## 1. المبدأ الأساسي

الاتجاه الحالي:

> **One Falcon Account → Multiple Application Subscriptions**

المستخدم ينشئ حساب Falcon واحد، ثم يستطيع الاشتراك في Application واحد أو أكثر.

لا يحتاج إلى حساب منفصل لكل Application.

لكن يجب الحفاظ على الفصل التالي:

```text
FALCON ACCOUNT
!=
APPLICATION SUBSCRIPTION
!=
APPLICATION ENTITLEMENT
!=
ACTION-SPECIFIC AUTHORIZATION
```

## 2. Create Account

المسار المرشح:

```text
Public Falcon Home
        ↓
Create Account
        ↓
Create Falcon Account
        ↓
Choose Applications
        ↓
Select one or multiple Applications
        ↓
Application-specific onboarding if required
        ↓
User Home / My Applications
```

المستخدم يستطيع اختيار أكثر من Application أثناء التسجيل نفسه.

مثال:

```text
Choose your Applications

☑ FSATS
☑ Accounting
☐ Warehouse

[ Continue ]
```

اختيار Application يعني طلب/إنشاء علاقة اشتراك وفق العقد النهائي، وليس تلقائيًا منح كل authority داخل ذلك Application.

## 3. Sign In

بعد نجاح Sign In يجب أن يأتي تحديد الهوية/الدور من مصدر authoritative معتمد مستقبلًا.

Shared Web لا يثبت من عنده أن الشخص Owner أو User.

مسار UX:

```text
Sign In
  ↓
Authoritative identity / role result
  ↓
┌──────────────────────┬─────────────────────────┐
│ Regular Falcon User  │ Project Owner           │
│        ↓             │        ↓                │
│ My Applications      │ Falcon Command Center   │
└──────────────────────┴─────────────────────────┘
```

### Owner Routing Rule

إذا كانت النتيجة authoritative تحدد المستخدم بأنه `Project Owner`:

> **Shared Web يوجهه مباشرة إلى `Falcon Command Center / Owner Page`.**

الـOwner لا يهبط أولًا على صفحة `My Applications` الخاصة بالمستخدم العادي.

من `Falcon Command Center` يستطيع فتح Applications والتنقل إليها حسب صلاحياته وعقودها الفعلية.

## 4. User Home / My Applications

المستخدم العادي يدخل إلى مساحة Falcon الخاصة به.

الهدف:

- عرض Applications المشترك بها.
- فتح Application.
- فتح Application في tab/window مستقل.
- عرض Applications أخرى متاحة للاشتراك عندما يكون ذلك مسموحًا.
- إدارة الاشتراكات من منظور UX.
- الوصول لإعدادات الحساب العامة المسموح بها.

مثال:

```text
Welcome to Falcon

My Applications

FSATS        [ Open ] [ Open in New Tab ]
Accounting   [ Open ] [ Open in New Tab ]

Available Applications
Warehouse    [ Learn More ] [ Subscribe ]
```

## 5. App Switcher

عند دخول المستخدم إلى أي Application، Shared Web يقدم مدخلًا موحدًا للتنقل بين Applications التي يملك وصولًا لها.

مثال:

```text
FALCON | FSATS ▼ | ... | User
```

القائمة:

```text
My Applications

✓ FSATS
  Accounting

Open Falcon User Home
Manage Applications
```

المستخدم يستطيع الانتقال مباشرة أو فتح Application آخر في tab مستقل.

---

## 6. Parallel Application Use

المستخدم قد يشغل أكثر من Application في نفس الوقت:

```text
Tab 1 → FSATS
Tab 2 → Accounting
Tab 3 → Falcon User Home
```

هذا مسموح كتجربة استخدام Candidate، لكن لا يخلق coupling بين Applications.

قواعد التخطيط:

- كل request يحمل Target Application واضحًا.
- كل result يعود إلى الطلب والـApplication الصحيحين.
- لا يوجد authority مبني على مفهوم ضمني مثل "الـApplication الحالي".
- فتح tab جديد لا يمنح صلاحية إضافية.
- Shared Web لا يخلط state أو result بين Applications.

`MULTIPLE TABS != SHARED BUSINESS STATE`

---

## 7. Subscription Management

المستخدم يجب أن يستطيع مستقبلًا، حسب العقود والسياسات المعتمدة:

- رؤية Applications المشترك بها.
- طلب الاشتراك في Application إضافي.
- معرفة حالة الاشتراك.
- بدء onboarding خاص بالـApplication إذا احتاجه.
- إدارة/إلغاء اشتراك عندما تكون هذه العملية مسموحة.

لكن Shared Web لا يفترض أن:

```text
SUBSCRIBE CLICK = SUBSCRIPTION ACCEPTED
UNSUBSCRIBE CLICK = APPLICATION REMOVED
```

النتيجة authoritative تأتي من الجهة المالكة للعلاقة/العقد عند تعريفها.

## 8. FSATS Onboarding Boundary

### Owner Clarification — 2026-08-14

قرار الـProject Owner الحالي للـUX والـFSATS onboarding هو:

> **User API / Broker Secret is required only when the user chooses automated trading.**

الاستخدامات غير التنفيذية مثل:

- الاستشارات؛
- التحليل؛
- التوصيات؛
- الاطلاع على المعلومات أو النتائج؛
- أي استخدام FSATS لا يطلب من النظام تنفيذ تداول آلي باسم المستخدم؛

**لا تتطلب من المستخدم إدخال API Key أو Broker Secret.**

المسار المرشح:

```text
Subscribe to FSATS
        ↓
Use advisory / analysis / recommendation features
        ↓
NO USER API / BROKER SECRET REQUIRED
```

أما عند اختيار المستخدم التداول الآلي:

```text
User chooses Automated Trading
        ↓
Automated-execution onboarding
        ↓
Request only the credentials actually required
        ↓
Validate through the authoritative Application/Foundation boundary
        ↓
Enable only after the required authority/readiness exists
```

القواعد:

```text
FSATS SUBSCRIPTION != AUTOMATED TRADING
CONSULTATION != EXECUTION AUTHORITY
ADVISORY USE != USER BROKER CREDENTIAL REQUIREMENT
USER API CREDENTIALS = AUTOMATED-TRADING-STAGE REQUIREMENT ONLY
```

هذا Owner clarification يتطلب مزامنة Application-side semantics عبر إعادة مراجعة FCR-0081. إلى أن يرد الـApplication، Shared Web يحفظ قرار الـOwner ولا يخترع تفاصيل API fields أو broker schema أو storage mechanism.

### Preserved Security Boundary

من رد FCR-0081 السابق تبقى الحدود الأمنية غير المتعارضة محفوظة:

- secret/key/token bytes لا تصبح reusable Web-owned state أو logs.
- Shared Web يعرض فقط non-secret metadata عندما يقدمه المالك authoritative.
- exact credential schema/storage/transfer binding غير مثبت بعد.
- إدخال المستخدم للـcredential لا يعني acceptance أو execution authority.

## 9. Phased Feature Access / VIP Direction

قرار الـOwner الحالي هو استخدام نموذج تجربة VIP واضح عند تسجيل مستخدم جديد في FSATS.

```text
NEW FSATS USER
      ↓
1 MONTH VIP TRIAL
      ↓
7 DAYS BEFORE TRIAL END
      ↓
EXPIRY WARNING + SUBSCRIBE + COMPARE VIP/STANDARD
      ↓
TRIAL ENDS WITHOUT SUBSCRIPTION
      ↓
STANDARD LIMITS APPLY
```

### 9.1 شهر VIP مجاني

كل مستخدم جديد يحصل على **شهر كامل من VIP** كتجربة أولية.

خلال هذه الفترة يستطيع تجربة القدرات المتقدمة التي تكون ضمن VIP في النموذج التجاري اللاحق، وفق الـentitlement الفعلي وما تسمح به الجهة المالكة لكل capability.

قبل انتهاء التجربة بـ**7 أيام**، تظهر للمستخدم رسالة واضحة بأن فترة VIP قاربت على الانتهاء.

الرسالة يجب أن تعطيه على الأقل:

- تنبيه واضح بموعد اقتراب انتهاء التجربة؛
- مسار للاشتراك للمحافظة على مزايا VIP؛
- رابط/مدخل إلى صفحة تشرح الفرق بين `VIP` و`Standard` بشكل مفهوم.

مثال UX تصوري فقط:

```text
Your VIP trial ends in 7 days.
Subscribe to keep your VIP features.
[ Compare VIP vs Standard ] [ Subscribe ]
```

### 9.2 المستخدم Standard بعد انتهاء التجربة

إذا انتهت تجربة VIP بدون اشتراك، يتحول المستخدم إلى حدود Standard.

بالنسبة للشارت، الاتجاه الحالي:

- يبقى لديه الشارت الأساسي؛
- يستطيع استخدام المؤشرات الفنية العادية المتاحة له؛
- بحد أقصى **4 مؤشرات نشطة في نفس الوقت**؛
- لا تتوفر له خاصية حفظ Presets / Layouts الجديدة؛
- تبقى الميزات المقفلة ظاهرة؛
- عند محاولة استخدامها يظهر مسار Upgrade واضح بدل خطأ غامض.

### 9.3 مدارس Falcon = VIP فقط

مدارس Falcon التحليلية تعتبر من القدرات الخاصة والمميزة في Falcon، ولذلك بعد انتهاء فترة التجربة:

```text
FALCON SCHOOLS = VIP ONLY
STANDARD USER = NO FALCON SCHOOL ACCESS
```

يمكن إبقاؤها ظاهرة للمستخدم Standard كقدرات VIP حتى يعرف ما الذي سيحصل عليه عند الترقية، لكن ظهورها لا يعني entitlement.

### 9.4 استراتيجية واحدة للمستخدم Standard على مستوى الاستخدام كله

المستخدم Standard يستطيع تشغيل **استراتيجية واحدة فقط في نفس الوقت وعلى سهم/أصل واحد فقط**.

هذا القيد ليس "استراتيجية واحدة لكل صفحة". إذا فتح عدة أسهم في tabs أو صفحات جانبية، لا يحصل على Strategy Slot جديد لكل سهم.

```text
STANDARD USER:
MAX ACTIVE STRATEGY = 1
MAX ASSETS WITH ACTIVE STRATEGY = 1
```

إذا كانت استراتيجية مفعلة على سهم A وأراد استخدام استراتيجية على سهم B، يجب أولًا إزالة/إيقاف الاستراتيجية من السهم A، أو الانتقال لمسار VIP عندما يكون ذلك مناسبًا.

```text
STRATEGY ACTIVE ON ASSET A
        ↓
TRY TO ACTIVATE ON ASSET B
        ↓
SECOND ACTIVATION BLOCKED
        ↓
REMOVE FROM ASSET A FIRST
OR UPGRADE TO VIP
```

### 9.5 VIP

المستخدم VIP يستطيع، ضمن الحدود التي تعتمدها Application والـentitlement النهائي:

- استخدام مدارس Falcon؛
- تركيب أكثر من مدرسة/استراتيجية في الوقت نفسه؛
- استخدام هذه التركيبات على أكثر من أصل إذا كانت capability authoritative تسمح بذلك؛
- حفظ Presets / Layouts واستخدام Default Presets؛
- الوصول إلى القدرات المتقدمة الأخرى التي تُعتمد ضمن VIP لاحقًا.

### 9.6 قواعد العرض والترقية

```text
INITIAL/TRIAL VIP ACCESS != PERMANENT VIP ENTITLEMENT
STANDARD USER != NO VALUE
VISIBLE OPTION != ENTITLED FEATURE
LOCKED PREMIUM FEATURE = VISIBLE
LOCKED PREMIUM FEATURE ATTEMPT = CLEAR UPGRADE PROMPT
VIP LABEL != VIP ENTITLEMENT
UI VISIBILITY != ACCESS AUTHORITY
SUBSCRIPTION TIER != ACTION AUTHORIZATION
UPGRADE PROMPT != AUTOMATIC UPGRADE
```

Shared Web لا يخترع حالة VIP ولا وقت بداية/نهاية التجربة من نفسه. الإتاحة النهائية وحالة التجربة والاشتراك يجب أن تأتي من مصدر entitlement authoritative عندما يتم تعريف مالك العقد وآليته.

لم يُحسم بعد:
- اسم خطة VIP النهائي؛
- السعر؛
- آلية الدفع؛
- exact entitlement/subscription contract owner؛
- القائمة النهائية الكاملة لكل مزايا VIP؛
- السياسة التفصيلية لبيانات/Presets التي أنشأها المستخدم أثناء تجربة VIP بعد انتهاء التجربة.

## 10. Owner Account Experience

الـOwner يستخدم نفس مفهوم Falcon identity العام، لكن تجربة ما بعد الدخول مختلفة.

```text
Owner Sign In
     ↓
Falcon Command Center
```

صفحة الـOwner المرشحة تتضمن:

- Falcon overview/status presentation from authoritative sources.
- Applications.
- Needs Your Attention.
- Users.
- Ask Falcon / Conversational Gateway.
- Falcon Control.
- Emergency / degraded-state access where authoritative capability exists.
- Activity / Audit.
- Settings.

ومنها يستطيع الـOwner فتح Application معين أو فتح أكثر من Application في tabs مستقلة.

## 11. Authority and Truth Rules

هذه القواعد لا تتغير بسبب سهولة الـUX:

```text
SIGNED_IN != SUBSCRIBED
SUBSCRIBED != AUTHORIZED_FOR_ACTION
ROUTE_EXISTENCE != AUTHORITY
DELIVERY != ACCEPTANCE
USER_REQUEST != APPLICATION_ACCEPTANCE
REQUEST_SENT != ACTION_ACCEPTED != ACTION_COMPLETED
```

Shared Web يعرض الحالة والنتيجة authoritative ولا يصنع business truth محليًا.

## 12. ما لم يتم حسمه بعد

لا يزال مفتوحًا للتصميم/الاعتماد المستقبلي:

- exact Authentication mechanism.
- exact Owner/User role source and verification mechanism.
- Session/SSO model.
- MFA/password/passkey choices.
- organization/company account model.
- entitlement/subscription contract owner and exact states.
- billing/payment/licensing model.
- exact automated-trading credential fields/schema.
- exact credential storage and secure transfer.
- final account recovery/security flows.
- final app-switcher technical routing.
- final VIP plan definition, pricing, feature list and migration policy.

هذه النقاط لا يتم اختراعها داخل Shared Web قبل وجود authority والعقود والمراجعات المطلوبة.
