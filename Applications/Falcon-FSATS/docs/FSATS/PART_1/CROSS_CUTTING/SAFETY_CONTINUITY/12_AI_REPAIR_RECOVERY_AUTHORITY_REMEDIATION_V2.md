# AI Repair / Controlled Recovery Authority Remediation V2

**Status:** `CONTROLLING REMEDIATION CANDIDATE / NOT_OWNER_ACCEPTED / NOT_CLOSED`

This record controls `09_AI_REPAIR_AND_CONTROLLED_RECOVERY_AUTHORITY_MATRIX_CANDIDATE.md` where the clauses below differ.

## 1. R1 Automatic Recovery Is Restoration-Only

R1 automatic recovery SHALL be limited to non-semantic restoration through one of the following:

1. exact restart/reload of an already-approved artifact/state whose identity and trust remain valid;
2. rollback to an exact previously approved trusted baseline;
3. an explicitly pre-authorized deterministic corrective action whose permitted state transition, target scope, bytes/configuration range, authority ceiling, validation obligations and rollback path were bounded before the incident.

R1 SHALL NOT introduce a new semantic candidate.

```text
R1 = RESTORE / REAPPLY ALREADY-GOVERNED TRUSTED STATE
R1 != CREATE-AND-ADOPT NEW INTELLIGENCE
```

## 2. R1 Exclusions

R1 automatic Controlled Revival is prohibited for:

- newly generated code;
- newly generated model logic or model replacement not already approved as the exact trusted target;
- new strategy, decision or policy logic;
- new architecture;
- authority or permission change;
- goal/purpose change;
- materially new learned/adaptive state not already accepted as the trusted target;
- self-development candidates;
- repairs whose actual changed semantics exceed the pre-authorized corrective envelope.

If any of these apply, the incident is at least R2 and may be R3 depending on scope and trust impact.

## 3. R2 Minimum Owner Gate

Any repair that creates or adopts new Application-owned code/model/behavioral semantics requires:

```text
CONTAIN
-> INVESTIGATE
-> ISOLATED CANDIDATE REPAIR
-> INDEPENDENT VALIDATION
-> OWNER APPROVAL
-> CONTROLLED REVIVAL
```

This remains true even when the candidate was generated by a trusted unaffected Awareness entity and even when all technical tests pass.

Technical PASS does not create adoption authority.

## 4. R3 Preserved

R3 remains mandatory for critical/unknown trust failures, protected architecture/goals/authority/permission changes, evidence/monitoring/containment interference, unknown blast radius, unavailable trusted baseline, safety-kernel trust loss, Factory Reset requiring higher governance, or other high-consequence governance changes.

## 5. Automatic Notification and Evidence

R1 may proceed without real-time Owner approval only when a valid pre-existing authorization explicitly permits it. Every R1 event must still be attributable, fully evidenced and visible to the Owner.

Owner silence does not create R1 authority.

## 6. Non-Grant

This documentary remediation defines a candidate authority boundary only. It does not itself establish any runtime R1 pre-authorization, implementation, deployment or production authority.
