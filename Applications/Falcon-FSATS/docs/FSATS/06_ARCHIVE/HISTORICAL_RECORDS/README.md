## Final accepted P0-A governing model

P0-A treats FSATS V1.3 as `HISTORICAL_DESIGN_REFERENCE`.

V1.3 must be reviewed for completeness and prior knowledge, but it is not a binding current baseline and has no veto authority over a stronger justified V1.4 design.

The accepted model distinguishes:

1. Falcon Vision and Constitution constraints;
2. applicable current Falcon governance/architecture/Foundation boundaries;
3. explicit Owner objectives and decisions;
4. historical V1.3 knowledge and validation evidence;
5. engineering/Architecture/Security/Red-Team assessment; and
6. realization/evidence state separately from governing meaning.

A better justified V1.4 design may retain, improve, align, replace or remove a V1.3 approach when the old problem/outcome has first been understood and the material difference, rationale, benefit and trade-offs are recorded.

When an Owner direction appears to conflict with Falcon Vision or Constitution, the process warns the Owner, explains the conflict and proposes compliant alternatives aimed at the same intended result.

## Planning lifecycle rule

```text
DRAFT
→ DESIGN DEVELOPMENT
→ ARCHITECTURE / CONSISTENCY REVIEW
→ RED-TEAM REVIEW
→ FINDINGS
→ REMEDIATION
→ FRESH CURRENT-VERSION RE-REVIEW
→ POST-CHANGE REPORT
→ OWNER REVIEW CANDIDATE
→ OWNER REVIEW
```

If Owner review requires a semantic change:

```text
OWNER_CONDITIONAL_APPROVAL_WITH_CHANGE
→ APPLY_OWNER_CHANGE
→ FRESH_ARCHITECTURE / CONSISTENCY REVIEW
→ FRESH_RED_TEAM REVIEW OF THE CHANGED VERSION
→ POST_CHANGE_REVIEW_REPORT
→ OWNER_FINAL_REVIEW
→ OWNER_FINAL_ACCEPTANCE / CLOSURE only if explicitly granted
```

A pre-change Red-Team report cannot validate a post-change artifact.

Technical PASS, Red-Team PASS, repository commits, conditional approval, or silence do not equal final Owner acceptance.
