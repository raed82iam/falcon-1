## 2026-08-15 Application semantic clarification ΓÇö broker-account identity, not user identity

Project Owner clarified the FSATS trading-side identity model prospectively:

```text
FSATS DOES NOT OWN CUSTOMER / USER IDENTITY.
FSATS DOES NOT TRACK USERNAME, CUSTOMER NAME, OR HOW MANY BROKER ACCOUNTS BELONG TO ONE PERSON.

TRADING OPERATING SUBJECT = BROKER ACCOUNT.
BROKER ACCOUNT ID = UNIQUE ACCOUNT IDENTIFIER PROVIDED BY THE BROKER.
MULTI-BROKER SAFE IDENTITY = BROKER ID + BROKER ACCOUNT ID (+ ENVIRONMENT WHERE REQUIRED).
```

The Shared Web Application owns the mapping from broker-account identity to the applicable customer/user/contact target. FSATS sends business/trading incident semantics addressed to the affected broker account; Web resolves that account to the customer and performs Web-owned notification/interaction.

Accordingly, the Application-side requirement in this FCR must not be interpreted as requiring FSATS to own or transport a Falcon customer/user ID. For future Stage 12 broker-execution egress, the required business/execution identity is account-centric and must preserve, as applicable:

- exact Application identity;
- exact BrokerId;
- exact broker-provided BrokerAccountId;
- exact environment;
- exact execution route/service/destination;
- exact order/submission/reconciliation identity;
- governed credential reference and authority evidence.

A broker-wide outage may legitimately affect multiple broker accounts. Account-local failures must remain account-local unless evidence proves a wider broker/shared-dependency blast radius.

This clarification creates no runtime, broker-connectivity, credential, Paper, Live, or Stage 12 implementation authority. Current `Waiting On: FOUNDATION` remains unchanged.
