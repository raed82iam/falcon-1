## Application response ΓÇö Guardian user-targeted notification and action semantics

### 1. User-targeted Guardian notifications

The current accepted Application design does **not** establish a canonical Guardian notification contract targeted to a specific authenticated user/principal. Guardian currently owns protection observation, incident qualification, protection scope/restriction/command governance, crisis survival coordination, and reconciliation/recovery protection evidence. P1-H defines exact protection-command target/scope semantics, but those targets are protection subjects/scopes, not a canonical user-notification principal model.

Therefore:

`GUARDIAN_USER_SPECIFIC_NOTIFICATION_CONTRACT = NOT_YET_CANONICALLY_DEFINED`

Shared Web SHALL NOT infer a target user or invent user-specific urgency/action semantics from Guardian incident/protection state.

### 2. Conditions requiring explicit user attention/action

The current Application design supports protection-relevant states and command/outcome truth such as anomaly, degraded state, material protection incident, integrity incident, unknown condition, command rejection, partial application, expiry/revocation, reconciliation-required state, stale/unknown Trading truth, Safety Kernel trust failure, and evidence-path failure. These conditions can legitimately be presented as authoritative Guardian state where exposed through governed contracts.

However, the current accepted design does **not** yet classify which of those conditions SHALL become a specific user's mandatory action-required notification. That mapping remains undefined and must not be invented by Web.

### 3. Semantics Web may safely distinguish today

Where governed projections/contracts expose the necessary state, Web may truthfully distinguish:
- informational/general Guardian state;
- severity/incident/protection state actually supplied by the owning Application contract;
- command/request sent;
- accepted/rejected;
- applied/partially applied;
- expired/revoked;
- reconciliation-required;
- stale/unknown/unavailable state.

But the following are **not yet established as generic Guardian notification contract states**:
- `USER_SPECIFIC_NOTIFICATION`;
- `URGENT_USER_SPECIFIC_NOTIFICATION`;
- `ACTION_REQUIRED_FOR_USER_X`.

Those require a later explicit Application-owned semantic definition before Web freezes Guardian-specific personal urgent/action-required UX.

### 4. Information required if/when user-targeted action semantics are defined

Any future Application-owned user-targeted Guardian interaction must preserve at minimum the same Falcon truth/authority invariants already governing cross-boundary commands and Web requests:
- attributable originating Application/Guardian identity;
- exact target principal/user identity or governed principal reference;
- semantic event/incident/action identity;
- severity/urgency only when authoritatively classified;
- whether user action is required versus merely recommended/informational;
- exact allowed action intent(s) where applicable;
- authority basis and authorization requirements;
- effective time and deadline/expiry where applicable;
- current state;
- correlation/causation identity;
- idempotency/replay semantics where applicable;
- acknowledgement/acceptance/outcome truth;
- stale/unknown/unavailable/revoked/expired handling;
- evidence/provenance required to prevent UI inference.

This is an Application-side required semantic envelope, not a prescribed Web schema or visual implementation.

### 5. Human-readable wording

The current accepted Application design does not require Guardian to own final reusable UI copy. The safer current boundary is:
- Application owns authoritative structured business/protection meaning, identity, severity when defined, target when defined, required-action meaning, allowed intent, authority semantics and outcome truth;
- Shared Web owns human-readable presentation/copy and reusable interaction UX, provided it does not weaken, upgrade, suppress or invent the authoritative meaning.

A future contract may optionally carry an authoritative summary/message field, but Web presentation must never treat prose alone as the source of authority.

### 6. Ownership boundary

Confirmed:
- **Application-owned:** Guardian protection/business meaning, incident classification, protection target/scope, urgency/severity where contractually defined, required-action semantics where defined, allowed action intent, authorization semantics, command/request outcome truth, correlation/causation/evidence.
- **Shared Web-owned:** reusable visual presentation, layout, interaction affordances, dialogs/popups, notification-center behavior, accessibility and responsive UX.

Web SHALL NOT become Guardian/Trading/Owner authority or invent missing Application semantics.

### 7. User-action request/acknowledgement/outcome truth

The existing cross-workstream invariant remains mandatory:

`UI_CLICK != BUSINESS_AUTHORIZATION`

`REQUEST_SENT != REQUEST_ACCEPTED != ACTION_COMPLETED`

For Guardian protection commands specifically, current P1-H also preserves distinct outcomes including sent, accepted/rejected, applied, partially applied, expired, revoked and reconciliation-required. Delivery never implies target acceptance or successful application.

## Owner-directed Application clarification ΓÇö per-user broker/API failure, Web notification, emergency shadow simulation

### 1. Scope and isolation

A broker/execution API failure tied to one specific user/principal/account SHALL be contained to that user/account unless evidence proves a broader shared failure.

`USER_A_API_FAILURE != USER_B_FAILURE != APPLICATION_FAILURE != FSATS_FAILURE`

Affected user/account immediately enters a no-new-risk restriction. Other independently healthy users continue normally.

### 2. Failure truth

When the affected user's broker API cannot be contacted at all, Falcon SHALL NOT claim current broker/account/order/position truth.

Falcon preserves:
- last broker-confirmed account snapshot and timestamp;
- last broker-confirmed open positions;
- last broker-confirmed working/protective orders;
- every locally recorded order request/submission attempt and its last proven outcome;
- any ambiguous/unconfirmed submission explicitly as `EXECUTION_TRUTH_UNKNOWN / RECONCILIATION_REQUIRED`.

`LAST_CONFIRMED_STATE != CURRENT_STATE`
`ORDER_SENT != BROKER_ACK != FILL`
`UNKNOWN != FAILED`
`UNKNOWN != SAFE_TO_RETRY`

- exact internal user/principal ID and permitted display name;
- affected broker/account/environment reference;
- failure class and first-detected time;
- last successful broker/API contact time;
- `NEW_RISK_RESTRICTED = TRUE`;
- confirmed open positions known before loss of contact;
- confirmed working/protective orders known before loss of contact;
- ambiguous order requests/submissions with exact status `NOT_PROVEN_EXECUTED_OR_NOT_EXECUTED`;

### 4. A-to-Z user actions

The Application shall provide ordered action semantics equivalent to:

A. Do not submit new Falcon trading actions for the affected account while the incident is active.
B. Log in directly to the broker using the broker's independent official interface.
C. Verify the exact current account/balance state.
D. Verify every open position.
E. Verify every working/open/pending order.
F. Verify every stop/protective order that Falcon last knew to exist.
G. For each ambiguous Falcon submission, determine at the broker whether it was rejected, accepted, partially filled, fully filled, cancelled, or remains working.
H. Take any immediately necessary protective action directly at the broker when exposure is unsafe and Falcon has no execution path.
I. Check whether the API key/token/credential is expired, revoked, disabled, permission-reduced, IP-restricted, or otherwise invalid.

Manual recovery must be treated as a slow degraded-control path. The risk model shall account for elapsed time across at least:
- broker UI refresh/capture delay;
- screenshot upload/transport delay;
- Falcon analysis delay;
- question/answer delay;
- human understanding/decision delay;
- human order-entry delay;
- broker acceptance/execution delay;
- market movement during the whole interval.

The effective manual-action risk estimate should therefore consider:

`TOTAL_MANUAL_LATENCY = evidence_age + upload_delay + analysis_delay + dialogue_delay + human_decision_delay + manual_entry_delay + broker_execution_delay`

- user/manual confirmation is not API-verified truth;
